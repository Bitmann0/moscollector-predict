# Первый backtest: технические сигналы насосов

## Происхождение

Отчёт перенесён из PR #3: ветка `feature/signal-backtest`, коммиты `703bc8b` и `607e27060978c7697be8d612e5de9f91e7ca7d92` от 15.09.2026, автор Bitmann0. [report.json](report.json) и [sources.json](sources.json) скопированы без изменений. К тексту при переносе добавлены разделы «Происхождение», «Связь с продуктом», «Что означает метка», «Отложенный период» и «Воспроизведение».

Код PR (`backend/ml/prepare.py`, `backtest.py`, `publish.py`) в main не переносился по решению D8 из [плана команды](../../../docs/superpowers/plans/2026-09-25-team-plan-to-submission.md). В main загрузку журнала, метку, временное разбиение и выбор порога делает пакет `ml/src/mkl`, насосы входят в голову D. Числа этого отчёта в main не пересчитываются.

## Результат

Precision **0.368**, Recall **0.226**. Цели Precision > 0,7 и Recall > 0,5 пока не достигнуты.

Цель: хотя бы одна запись «Неисправен» в следующие календарные сутки после суток без такой записи. Единица оценки — наблюдаемый канал-день. Это метрики сигнала; подтверждённых физических отказов в выборке нет.

## Протокол

- Обучение: 2024; выбор модели: январь–сентябрь 2025; выбор порога: октябрь–декабрь 2025.
- Финальный тест: январь–июнь 2026. Его исходы не участвуют в выборе модели и порога.
- Окна признаков: предыдущие 1 и 7 суток. Целевое окно: следующие 24 часа.
- Граница t — полночь Europe/Moscow (предположение); признаки [t−7d,t), цель [t,t+24h).
- Цели, пересекающие границу следующего периода, исключаются.
- Вчерашняя запись «Неисправен» исключает точку из прогнозирования.
- Дни с неполным глобальным покрытием и отсутствием будущих наблюдений канала исключаются.
- Отдельный августовский пример не смешивается с годовой историей.

Выбрана модель `hist_gradient_boosting`; порог 0.201045. На периоде выбора порога ограничение Precision > 0,7 при минимум 10 уведомлениях не выполнено; использован заранее заданный запасной критерий F0.5.

## Связь с продуктом

Постановка «насос, следующие 24 часа» в продукте не используется. Насосы входят в голову D: метка `label_wear` строится функцией `build_wear` в [labels.py](../../../ml/src/mkl/labels.py) по шести типам оборудования из `EQUIPMENT_STYPES`, горизонт 7 суток, до трёх рекомендаций в сутки, после выдачи канал 7 суток не попадает в выдачу повторно ([heads.yaml](../../../ml/configs/heads.yaml), `apply_issued_cooldown` в [serve.py](../../../ml/src/mkl/serve.py)). С коммита `88605f6` (#17) D выдаёт рекомендации по правилу `n_bad_w7`, а не по модели: [RULE_VS_MODEL_RESULT.md](../../../ml/reports/RULE_VS_MODEL_RESULT.md). Временная проверка модельной политики D — [D_LIVE_POLICY_TEMPORAL.md](../../../ml/reports/D_LIVE_POLICY_TEMPORAL.md).

Числа этого отчёта нельзя ставить в одну таблицу с D. Здесь один тип датчика «Состояние насоса», окно 24 часа, единица — канал-день без суточного лимита, 397 уведомлений за тест. У D единица та же, канал-сутки, но другие цель, горизонт, шесть типов датчиков вместо одного и бюджет. По решению D12 числа для документов, слайдов и README берутся только из реестра `ml/reports/SUBMISSION_METRICS.md` (ML1-08). В main этого реестра пока нет, и числа отчёта в него не вносились, поэтому в документах сдачи и на слайдах их не цитируют.

## Покрытие и ограничения

Из 164160 календарных канал-дней допустимы по истории 26327; ещё 5944 имеют неизвестный будущий исход. Оценено 20383 точек во всех периодах.

Метрики условны на этом покрытии: они не распространяются на молчащие каналы. Наличие событий во всех 24 часовых корзинах не доказывает полноту выгрузки. Совместные «Неисправен» и «Норма» не упорядочиваются искусственно. Канал-дни не равны независимым эпизодам физических отказов. Оценка 24-часового окна не доказывает предупреждение минимум за 24 часа.

Измеренное предсказание 5849 тестовых точек: 0.0085 с (только inference готовых признаков, не полный потоковый SLA).

## Что означает метка

PR #6 воспроизвёл этот прогон байт в байт: SHA-256 `pump_daily.csv` и `coverage.csv` и все метрики теста совпали ([pump-validation-review](../pump-validation-review/README.md)). Там же проверено, что стоит за меткой. У каналов «Состояние насоса» за 2024 — июнь 2026 «Неисправен» записан в 41 952 секундах, и в 41 851 из них (99,76 %) у того же канала в ту же секунду есть другое значение, чаще всего «Обесточен» (39 472 секунды). Модель предсказывает появление сообщения «Неисправен», а не отказ насоса.

## Отложенный период

Тест 01.01–30.06.2026 совпадает с отложенным периодом main: `HOLDOUT_START` и `HOLDOUT_END` в [config.py](../../../ml/src/mkl/config.py). В счётчик [holdout_uses.md](../../../ml/reports/holdout_uses.md) (38 просмотров) этот прогон не попал: [holdout_uses.py](../../../ml/scripts/holdout_uses.py) считает только записи `FINAL` из `ml/experiments/log.jsonl`, а код PR #3 туда не пишет. Значит, числа отчёта — ещё один просмотр 2026H1, а не результат запечатанного теста. Подбирать по ним что-либо в D или A_link нельзя.

## Воспроизведение

Только на замороженном коммите `607e270`: в main этих модулей нет. Ветка `feature/signal-backtest` по решению D8 не удаляется. Команды взяты из `docs/ml-development.md` этого коммита, пути к данным передаются явно:

```bash
git worktree add ../pump-signal-v1 607e270
cd ../pump-signal-v1
python3.12 -m venv .venv-ml
.venv-ml/bin/pip install -r requirements-ml.txt
.venv-ml/bin/python -m ml.prepare --dataset-zip /путь/dataset.zip --catalog /путь/справочник_каналов_датчиков.csv
OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 .venv-ml/bin/python -m ml.backtest
.venv-ml/bin/python -m ml.publish
```

Что нужно для запуска:

- `dataset.zip` с архивами `dataset/ext-journal-2024.7z`, `dataset/ext-journal-2025.7z` и `dataset/ext-journal-2026.7z`: их ищет `extract_year` в `backend/ml/prepare.py`. По `docs/ml-development.md` на архивы и CSV нужно около 8 ГБ свободного места, DuckDB ограничен 2 ГБ памяти.
- Справочник каналов. В прогоне PR #3 у него SHA-256 `fa550d4c…` ([sources.json](sources.json)). `prepare.py` берёт из справочника только `ид_канала_данных` и `тип_датчика`. В справочнике, опубликованном 16–23.09, у обоих полей 0 изменений, ID не добавлены и не удалены ([catalog_update_audit.json](../../catalog_update_audit.json)). Вывод из этого, прогоном не проверенный: с новым справочником набор насосных каналов и `pump_daily.csv` будут те же, изменится только `catalog_sha256` в манифесте.
- Linux. `prepare.py` пишет CSV через `DataFrame.to_csv` без `lineterminator`, и pandas 2.3.3 из `requirements-ml.txt` берёт `os.linesep`. На Windows строки получат CRLF, и SHA-256 CSV разойдутся с `input_sha256` в [report.json](report.json). Вывод сделан по коду, на Windows не проверялся. Адаптер PR #6 пишет CSV с `lineterminator="\n"`.

`ml.publish` в том worktree перезапишет `report.json`, `sources.json` и `README.md` в `docs/experiments/pump-signal-v1/`; README получится по шаблону PR #3, без разделов, добавленных при переносе.

На `mkl` этот прогон не пересчитывается по трём причинам. Признаки PR #3 (`faults_*`, `power_loss_*`, `ambiguous_seconds_*`) считаются по секундам с конкретными значениями, а в `daily_channel` из `ml/src/mkl/panel.py` таких столбцов нет, так что бэктест пришлось бы писать заново. Ключи дедупликации разные: `ml/src/mkl/ingest.py` удаляет дубли по полному кортежу вместе с `ид_события`, `prepare.py` — по каналу, времени, флагу тревоги и значению; строки, которые различаются только `ид_события`, `mkl` оставит, поэтому без отдельной сверки совпадение входов не гарантировано. И новый прогон стал бы ещё одним просмотром 2026H1.
