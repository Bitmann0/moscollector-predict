2. Описание работы компании, сервиса и актуальности задачи
АО « Москоллектор» — организация, которая отвечает за эксплуатацию и обслуживание
инженерных коллекторов Москвы. Компания управляет обширной инфраструктурой:
• 825 км коллекторов;
• 19,7 тыс. км кабелей связи;
• 8,3 тыс. км силовых кабелей;
• 1,9 тыс. км тепловых и водопроводных сетей (теплотрасс).
В настоящее время компания использует систему мониторинга и диспетчерскую службу для
контроля состояния объектов. Однако существующий подход имеет ряд существенных
недостатков:
• реактивный характер работы — специалисты реагируют только после срабатывания
датчиков;
• ложные тревоги составляют значительную часть всех срабатываний;
• обслуживание оборудования проводится по фиксированным срокам без учета реального
состояния.
Внедрение современных технологий становится критически важным для развития ЖКХ. Это
соответствует:
• Стратегии развития строительной отрасли и ЖКХ РФ до 2030 года;
• Национальной стратегии развития ИИ;
• Федеральному проекту ИИ в рамках национального проекта «Экономика данных».
Предлагаемый сервис прогнозирования инцидентов и управления ремонтными работами
позволит:
• заранее выявлять потенциальные риски отказов оборудования;
• снижать количество ложных тревожных выездов на объекты за счет выявления
ложных сработок;
• повышать эффективность эксплуатации инфраструктуры;
• оптимизировать затраты на обслуживание;
• повышать безопасность эксплуатации инженерных систем.
Сервис будет решать следующие задачи:
• прогнозирование отказов датчиков и инженерных систем до их фактического
возникновения;
• раннее выявление рисков возникновения инцидентов;
• повышение безопасности эксплуатации инженерных коллекторов;
• оптимизация процессов технического обслуживания;

3. Предназначение разрабатываемого сервиса
Сервис прогнозирования инцидентов предназначен для повышения эффективности
управления эксплуатацией инженерной инфраструктуры АО «Москоллектор» путем внедрения
современных технологий предиктивной аналитики.
Сервис направлен на решение следующих ключевых задач:
• прогнозирование отказов инженерных систем до их фактического возникновения;
• оптимизация работы диспетчерской службы;
• оптимизация процессов технического обслуживания;
• повышение безопасности эксплуатации инженерных коллекторов.
Сервис будет использоваться для:
• мониторинга общего состояния инженерных систем коллекторного хозяйства;
• контроля работы датчиков инженерных систем и систем безопасности;
• поддержки планирования профилактических работ;
• аналитической поддержки при управлении инцидентами;
Основными пользователями сервиса являются:
• диспетчеры объединённой диспетчерской службы и эксплуатационных подразделений;
• технический персонал по обслуживанию коллекторов;
• руководители эксплуатационных подразделений.
На основе предиктивного анализа система формирует прогнозы возможных инцидентов и
рекомендует превентивные меры.
4. Постановка задачи
Разработать сервис предиктивной аналитики для прогнозирования инцидентов и
поддержки принятия решений при планировании ремонтных работ в инженерных коллекторах
Москвы. Сервис должен обеспечить:
• автоматизированное выявление потенциальных рисков и угроз;
• оптимизацию работы диспетчерской службы за счет предоставления аналитических
данных;
• повышение эффективности технического обслуживания инженерной инфраструктуры.
В рамках реализации проекта сервис должен решать следующие задачи:
• прогнозирование отказов датчиков и инженерных систем до их фактическог о
возникновения;
• раннее выявление рисков возникновения пожаров и подтоплений;

• аналитическую поддержку при верификации фактов несанкционированного доступа;
• формирование рекомендаций по проведению технического обслуживания на основе
данных о состоянии оборудования.
5. Границы решения
Сервис должен:
• анализировать исторические и текущие данные мониторинга;
• обрабатывать информацию из журналов диспетчерской службы;
• работать с реестрами оборудования;
• предоставлять прогнозы инцидентов с указанием вероятности и временного горизонта;
• осуществлять предиктивное моделирование инцидентов на основе исторических данных;
• интегрироваться с существующими системами мониторинга для получения данных.
Сервис НЕ должен:
• замещать работу диспетчеров;
• принимать окончательные решения об инцидентах;
• управлять инженерным оборудованием напрямую;
• проводить ремонтные работы.
Сервис обязан обеспечивать:
• точность прогнозов не ниже установленных показателей;
• своевременное информирование о потенциальных угрозах;
• удобный интерфейс для работы диспетчеров;
• надежную интеграцию с существующими системами;
• защиту данных от несанкционированного доступа.
6. Общие требования к сервису
Прогнозирование инцидентов
• Анализ данных с датчиков для выявления потенциальных рисков инцидентов.
• Расчет вероятности инцидентов с горизонтом прогнозирования не менее 24 часов.
• Определение локации оборудования, подверженного риску.
• Классификация типов прогнозируемых инцидентов.
Сценарный анализ инцидентов
• Анализ сценариев инцидентов (пожар, проникновение, подтопление) на основе
исторических данных.
• Формирование превентивных уведомлений об инцидентах на основе прогнозных
моделей.

7. Требования к обработке данных
Входные данные
• Исторические данные (импорт из файлов CSV/XLSX).
• Потоковые данные из системы мониторинга СМВУ (интеграция по API/очереди
сообщений).
• Журналы ОДС (загрузка через API).
• Реестр оборудования (цифровой формат).
Примечание: все передаваемые данные должны проходить процедуру обфускации
(обезличивания) на стороне источника.
Форматы и способы обмена данными
• Файловый обмен: CSV, XLSX.
• Программный обмен (API): JSON, XML.
• Взаимодействие с СУБД: поддержка подключения к PostgreSQL (или иной СУБД,
используемой в инфраструктуре).
• Геоданные: GeoJSON, WKT (Well-Known Text).

9. Требования к производительности и качеству прогнозирования
Производительность
• Время формирования прогноза (inference) для одного объекта: не более 5 минут.
• Время обработки потоковых данных: в режиме, близком к реальному времени (задержка
не более 5 минут).
• Система должна поддерживать одновременную работу всех пользователей без
деградации производительности.
Качество прогнозирования
• Целевые показатели точности (Precision) и полноты (Recall) определяются на этапе
проектирования исходя из качества предоставляемых данных.
Горизонт прогнозирования
• Сервис должен обеспечивать формирование прогнозов с горизонтом не менее 24 часов.
10. Требования к пользовательскому интерфейсу и интеграции
Требования к пользовательскому интерфейсу
• Аналитическая панель (Дашборд): веб-интерфейс для диспетчеров с визуализацией
уровней риска.
• Интерактивная карта: отображение объектов инфраструктуры с выделением
проблемных зон.
• Журнал прогнозов: реестр событий с историей прогнозов и результатами их отработки.
• Система уведомлений: оповещение пользователей о критических инцидентах в режиме
реального времени.
Требования к интеграции
• API-интерфейс: наличие REST API для получения данных из внешних систем.
• Интеграция с системами мониторинга: получение данных о состоянии оборудования (в
режиме чтения).
• Синхронизация с базой оборудования: автоматизированное получение актуальных
реестров оборудования из учетных систем Заказчика.

12. Возможные пользовательские пути
Пример пользовательского сценария: Прогнозирование пожара в инженерном
коллекторе
Участники сценария:
• диспетчер (основной пользователь);
• аналитик (ответственный за верификацию данных).
Предпосылки:
• в системе накоплены исторические данные об инцидентах;
• система интегрирована с датчиками мониторинга и реестром плановых работ.
Шаги сценария:
1. Анализ данных: система в автоматическом режиме сопоставляет текущие показания
датчиков (температура, задымление) с данными о плановых работах и историческими паттернами.
2. Формирование прогноза: при выявлении аномалий система рассчитывает вероятность
инцидента и формирует предупреждение.

3. Уведомление: диспетчер получает уведомление на дашборд с указанием вероятности,

4. Верификация: диспетчер анализирует данные, при необходимости использует внешние

5. Принятие решения: диспетчер фиксирует решение в системе (например, «выезд бригады»

6. Завершение: информация о принятом решении сохраняется в журнале
для последующего анализа и дообучения модели.
Пример пользовательского сценария: Прогнозирование инцидента (подтопление)
Участники сценария:
• диспетчер (основной пользователь);
• аналитик (ответственный за верификацию данных).
Предпосылки:
• в системе накоплены исторические данные о подтоплениях;
• система интегрирована с датчиками мониторинга и внешними источниками метеоданных.
Шаги сценария:
1. Анализ данных: система в автоматическом режиме сопоставляет данные о частоте
включения насосных станций с прогнозом метеослужб и историческими паттернами
подтоплений.
2. Формирование прогноза: при выявлении аномалий система рассчитывает вероятность
инцидента и формирует предупреждение.
3. Уведомление: диспетчер получает уведомление на дашборд с указанием вероятности,
временного горизонта и локации объекта.
4. Верификация: диспетчер анализирует данные, при необходимости использует внешние
источники (например, камеры наблюдения) для подтверждения ситуации.
5. Принятие решения: диспетчер фиксирует решение в системе (например, «направление
бригады на проверку» или «мониторинг ситуации») с выбором причины из справочника.
6. Завершение: информация о принятом решении сохраняется в журнале
для последующего анализа и дообучения модели.
Результат:
• своевременное информирование диспетчера о рисках подтопления;
• фиксация принятых мер в системе;
• накопление данных для повышения точности будущих прогнозов.

13. Источники данных
Внутренние источники
• Система СМВУ: данные с датчиков (контактные, объемные, температурные, дымовые,
газовые). Интеграция осуществляется в режиме, близком к реальному времени (near real-time).
• Журналы ОДС: записи о срабатываниях, история инцидентов (глубина данных —
не менее 12 лет).
• Реестр оборудования: строительные конструкции (люки, вентшахты, камеры),
электрооборудование (насосы, вентиляторы), датчики.
Внешние источники
• Метеорологические службы: данные о температуре, влажности, осадках, атмосферном
давлении (интеграция через открытые API).
• Нормативная документация: Регламент технической эксплуатации коммуникационных
коллекторов (РТЭК).
Важные аспекты обработки
• Безопасность: интеграция с внутренними системами Заказчика осуществляется
исключительно в режиме «только чтение» (Read-only).
• Хранение: данные разделяются на оперативный контур, архивные данные
и аналитические витрины.
