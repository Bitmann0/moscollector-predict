# Обзор реализации другой модели

Проверен `Bitmann0/moscollector-predict`, ветка `main`, коммит `2abe71f`, 15.09.2026. Код приложения не изменялся. Это отдельный обзор реализации после аудита данных.

## Что добавлено

- `bc1d71d`: FastAPI API, статический веб-интерфейс, эвристическая модель по событиям каналов, SQLite-черновики заявок, CLI, тесты и архитектура.
- `9a43e68`: наш полный аудит ТЗ и данных, результаты и скрипты.
- `2abe71f`: Dockerfile, Compose, GitHub Actions, автономные синтетические тестовые данные, CONTRIBUTING и упаковка статических ресурсов.

Основные папки: `backend/app` — приложение; `tests` — четыре теста и фикстура; `docs` — архитектура и следующие этапы; `analysis` — наш аудит; `.github/workflows` — CI. `data/raw` предназначена для локальных исходников и исключена из Git.

## Что действительно работает

- Чтение однодневного примера и справочника каналов, проверка обязательных колонок и дат.
- Агрегация количества событий, тревог, коротких интервалов и повторяемости значений.
- Получение списка и карточки ранга риска через API, поиск и фильтрация.
- Создание черновика заявки и защита от повторного создания при последовательных запросах.
- Массовое создание черновиков для high/critical по команде пользователя.
- Дашборд со схемой каналов, очередью и таблицей.
- CLI для анализа, инструкция запуска, конфигурация через переменные окружения.

Карта подписана в CSS как схема без геокоординат; точки детерминированно вычисляются из ID. Это не реальная топология. В интерфейсе и API также есть отметка непроверенного baseline. Эти ограничения не полностью скрыты.

## Результаты запуска

Установлено отдельное окружение с зависимостями проекта. `pytest -q`: **4 passed**. `ruff check backend tests`: **All checks passed**. Есть два предупреждения об устаревающих интерфейсах зависимостей, не падения тестов.

На исходном примере: 169 993 события, 1 241 канал, обработка около **0,54 секунды** на текущем компьютере. Получено 48 critical, 41 high, 76 medium, 1 076 low. Это распределение эвристики, не подтверждённые неисправности. Главная страница и проверенные API возвращают 200; создание и повторное создание черновика работают.

## Существенные проблемы

### 1. [P1] Неправильный разбор булева флага

`backend/app/model.py:79`: `astype(bool)` считает непустую строку истинной. Воспроизведено: входные `f, t` превращаются в `True, True`. Так записаны флаги в годовых архивах. Пример с распознанными pandas `true/false` этого дефекта не показывает. Нужен явный словарь допустимых значений и отказ для неизвестных кодов.

### 2. [P1] Старая история получает текущую дату прогноза

`backend/app/model.py:159`: прогноз датируется текущим UTC-временем независимо от конца входной истории. В запуске 15 сентября данные до 1 августа стали основанием для «прогноза» до 16 сентября. `health` при этом сообщает готовность. Нужны раздельные время данных, время расчёта, режим исторического воспроизведения и проверка допустимой давности.

### 3. [P1] Горизонт не участвует в расчёте

`backend/app/model.py:150–160`: фиксированные коэффициенты дают ранжирующий балл. `horizon_hours` меняет срок действия и подпись, но не модель. Воспроизведено: 24 и 168 часов дают одинаковые риски для всех каналов. Нет обучения, целевых исходов, backtest и калибровки. Это эвристическое ранжирование состояния, а не проверенный прогноз будущего отказа.

### 4. [P1] Частота измерений может доминировать над смыслом сигнала

Формула использует частые события, число тревог и долю одинаковых значений, но не различает штатный режим опроса разных приборов. Численные величины температуры/газа в сам риск не входят. 42 из первых 50 каналов на реальном примере — газовые. Первое место: канал 278301, 83,65%, 6 229 записей, 0 тревог. Это не доказательство ложности оценки, но без истории отказов нет основания связывать такой балл с необходимостью замены.

Дополнительно масштаб количества событий определяется по всем активным каналам одновременно. Изменение состава выгрузки может менять оценку канала без изменения его собственной истории. Аналоговые типы включают «Тепловой датчик», хотя семантика его событий требует отдельной проверки.

### 5. [P1] Рекомендации не подтверждены нормативами

`backend/app/model.py:97`: для critical жёстко написано «проверить в течение 4 часов и подготовить замену». Основания срока и необходимости замены не представлены. До согласования с заказчиком нужны рекомендации уровня проверки, а не неподтверждённый срок/диагноз. Precision > 0,7 и Recall > 0,5 в документации — выбранные авторами ориентиры, не численные требования исходного ТЗ.

### 6. [P1, статическая проверка] Возможная ошибка первого запуска Compose

Compose направляет SQLite в `/app/state/moscollector.db` и подключает именованный volume к `/app/state`. Dockerfile создаёт и передаёт права только на `/app/data`, затем переключается на непривилегированного пользователя `app`. Для свежего volume необходимо обеспечить права на `/app/state`; сейчас ожидается ошибка записи. Docker в среде отсутствует, поэтому контейнерный запуск не проверен и этот вывод требует воспроизведения на Docker.

### 7. [P2] Healthcheck проверяет HTTP, а не готовность

При отсутствии файлов API возвращает HTTP 200 с `ready:false`. Docker HEALTHCHECK проверяет только успешность `urlopen`, поэтому отсутствие данных будет считаться успешным healthcheck. Воспроизведён ответ API; контейнер не запускался. Можно разделить liveness и readiness, явно определив их смысл.

### 8. [P2] Незавершённые интерфейс и жизненный цикл

Кнопки боковых разделов не имеют обработчиков. «Журнал прогнозов» — текущий список в памяти, без сохранённой истории. Черновики заявок сохраняются, но нет изменения статусов, закрытия, назначения, причин решения, исхода выезда и обратной связи. Переход к строке карты также зависит от наличия этой строки среди отображённых первых 300.

### 9. [P2] Обработка данных ограничена примером

Используются только два жёстко названных файла: пример событий и каталог каналов. Справочник диспетчерских объектов не читается, годовые архивы не импортируются. Расчёт выполняется один раз при запуске; нет API ingest, обновления данных и фонового пересчёта. Нет поддержки событийных конфликтов, дедупликации, неполного покрытия и семантики одновременных состояний из нашего аудита.

### 10. [P2] Соединения SQLite не закрываются явно

`with sqlite3.Connection` управляет транзакцией, но код не вызывает `close`. Во время дополнительной проверки временный файл БД в Windows оставался занят после выхода из клиента; сборка мусора позволила завершить очистку. Нужны явное закрытие соединений и отдельная проверка конкурентного создания черновика. Последовательная идемпотентность уже проверена, конкурентная пока нет.

### 11. [P2] Импортированные строки попадают в HTML без экранирования

`backend/app/static/app.js`: имя датчика, локация и факторы вставляются в `innerHTML`. Если источник содержит HTML, он может стать разметкой страницы. Для внешних/редактируемых данных нужен безопасный вывод текста. Наличие вредоносных строк в выданном датасете не утверждается.

## Что не закрыто по ТЗ

Подтверждённый прогноз на горизонте 24 часа; вероятности и оценка качества на будущем периоде; реальные объекты/география; журналы ОДС; интеграция мониторинга и заявок; потоковая обработка; полноценный журнал решений; PostgreSQL; роли и авторизация; LDAP/AD; аудит действий; backup/restore; проверка 20 одновременных пользователей. Docker и CI полезны, но CI пока только собирает образ, не проверяет старт Compose и готовность приложения.

## Следующие действия

1. Исправить `t/f`, время и свежесть данных; переименовать недоказанный процент в индекс риска, сохранив прозрачное описание.
2. Проверить и исправить старт Compose, готовность и закрытие соединений.
3. Подключить подготовленную историю и правила качества из аудита.
4. Определить один прогнозируемый исход, построить baseline и временную оценку.
5. Доделать сохранение прогнозов и решений диспетчера, затем интерфейс заявок.

Новые изменения в репозитории предполагаются через отдельные ветки и PR согласно добавленному `CONTRIBUTING.md`. Этот обзор сохранён локально, исправления и новый push не выполнялись.
