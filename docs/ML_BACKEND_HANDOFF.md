# Что передать бэкендеру от ML, 25.09.2026

Это задача на интеграцию и эксплуатацию. Бэкендер не меняет определения
меток, пороги, лимиты, порядок ранжирования или статус голов без согласования
с ML. ML отдаёт версионированный расчёт и принимает решения диспетчера как
будущие метки.

## Граница ответственности

**Бэкендер закрывает полностью:** загрузку и проверку новых файлов, запуск по
расписанию, базу прогнозов, идемпотентность, историю решений, права доступа,
API/UI, подтверждение заявки человеком, мониторинг свежести, ошибки,
нагрузочный замер и деплой.

**ML закрывает:** смысл целевого события, event-time метку, признаки, версию
метода, порог и бюджет, временной бэктест, baseline, precision/recall/unknown
и решение показывать голову или отложить её.

Нельзя автоматически включать любую модель, лежащую в каталоге `models/`.

## Какой пилот собираем

Показываем **рекомендации для проверки человеком**, основанные на будущих
событиях СМВУ. Это не подтверждённые аварии и не автоматическое распоряжение
на выезд. Числа ниже получены на уже многократно просмотренных периодах
и по прокси-меткам; их нельзя выдавать за независимую оценку качества реальных
аварий. Плановые Precision > 0,7 и Recall > 0,5 одновременно не доказаны.

отказа на последнем периоде стала Precision 0,084, Recall 0,472. Пожарная `B`
имеет низкую точность. Их не включаем в штатную очередь на выезд ради красивого
количества сценариев. См. [итоговый аудит](../reports/final.md),
[описание поставки](CUSTOMER_DELIVERABLE.md) и
[операционную проверку C](../reports/INTRUSION_OPERATIONAL_QUEUE.md).

## Что уже готово для интеграции

- `GET /health`, `/api/v1/directions`, `/api/v1/alerts`,
  `/api/v1/alerts/{id}`, `/api/v1/coverage`, `/api/v1/work-orders`,
  `/api/v1/work-orders/{id}` и отдельные ручные очереди
  `/api/v1/guard-signal-priorities`, `/api/v1/guard-weekly-inspections`
  в `src/mkl/api.py`.
- Версионированная структура алерта, `alert_id`, `case_key`, адрес, окно
  прогноза, версия модели и объясняющие факторы в `src/mkl/contract.py`.
- Генератор **черновика** заявки с группировкой по объекту в
  `src/mkl/workorders.py`. Это вычисляемое представление: подтверждения,
  постоянного хранения и отправки заявки во внешнюю систему пока нет.
- `coverage` отдельно показывает, где прогноз не строится. Пустая выдача
  не равна отсутствию риска.

## Что бэкендер может решать самостоятельно

Выбор веб-фреймворка, схемы PostgreSQL, очереди фоновых задач, механизма
авторизации, деплоя, способа хранения истории и устройства UI. Можно обернуть
существующий ML API либо вызывать `mkl.service` из общего процесса. Главное —
сохранить смысл и версии полей контракта; изменение схемы согласовать с ML.

## Что попросить сделать обязательно

### Непосредственный контракт для запуска D

ML-функция `mkl.service.alerts_for_head("D", asof, with_factors=...,
issued_history=[(ch, sent_day), ...], history_complete_from=...)` принимает
журнал **выданных диспетчеру** рекомендаций за предыдущие семь календарных
суток. `ch` — целочисленный ID канала, `sent_day` и
`history_complete_from` — `datetime.date`. Пустой журнал допустим, если
бэкенд может гарантировать его полноту начиная не позже `asof - 7 суток`.
Сохранять в журнал только строки с `in_budget=True` после применения ML-policy;
запись за текущие сутки не должна подавлять идемпотентный повторный расчёт.
Рекомендации с тем же каналом за прошлые 1–7 суток подавляются без заполнения
освободившегося места в лимите. При отсутствии/неполноте журнала явный вызов
D возвращает ошибку; ML не подменяет его сырым top-3. Общий `/alerts` пока не
включает D, пока бэкенд не подключит этот журнал к выдаче. Проверить сквозным
тестом два запуска одного дня и переход через восьмой день.

Исследовательские `B`, `C`, `A_strict` и другие модели без `product_status:
pilot` исключены из общей ML-выдачи даже при наличии `.pkl`. Недельная
охранная очередь идёт отдельным API. Текущий `A_link` с сохранённым
недопустимым порогом воздерживается от выдачи; нельзя переопределять его
top-20 на бэкенде.

1. **Отделить видимость головы от наличия обученной модели.** Конфигурируемый
   список разрешённых сценариев для пилота. Разрешённый ML-пилот сейчас:
   недельная охранная очередь и `D` с максимумом 3/сутки после подключения
   журнала рекомендаций. `A_link` с текущим сохранённым порогом воздерживается
   от выдачи; включать его можно только после нового решения ML. Не формировать
   реальные заявки из всех голов, которые случайно оказались в `models/`:
   `C` v1, `B`, onset и остальные исследовательские головы нельзя показывать
   как рабочую гарантию.
2. **Хранить прогнозы и решения.** На каждый запуск сохранять `asof`, время
   расчёта, `model_version`, версию данных/справочника, `alert_id`, `case_key`,
   риск, статус покрытия и результат диспетчера: проверено/отложено/ложный
   сигнал/подтверждено. Повторный расчёт обновляет тот же `alert_id`, не
   создаёт дубль; история прежних версий остаётся доступной для аудита.
3. **Заявка только после решения человека.** Черновик можно показать сразу;
   перевод в подтверждённую заявку, закрытие и комментарий должны храниться
   постоянно. Повторные алерты по одному `case_key` связывать с тем же случаем.
4. **Добавление новых данных без полной пересборки истории.** Приём новой пачки
   событий и справочника, проверка схемы/дубликатов/времени, инкрементальный
   расчёт нового дня, затем скоринг. Нужны статус последней успешной загрузки,
   число принятых/отклонённых строк и безопасный повтор запуска. Полный
   пересчёт признаков сейчас занимает 4 949 секунд и не укладывается в
   требование задержки 300 секунд.
5. **Показывать неполноту и ошибки явно.** `no_data`, `stale`, неизвестный адрес,
   неподдерживаемый объект, отсутствующая модель, ошибка расчёта, дата и
   свежесть данных — отдельные состояния. Сейчас `service.daily_alerts()` при
   некоторых ошибках пропускает голову, а API кэширует результат по дате без
   автоматического сброса после новых данных; эти состояния нужно закрыть.
6. **Замерить развёртывание на CPU в Linux.** Отдельно время приёма, расчёта
   новых признаков и скоринга; проверить несколько новых дней подряд и
   20 одновременных пользователей. Конкретное железо жюри не названо.

## Минимальный backend deliverable

Считать интеграцию выполненной после одной сквозной демонстрации:

1. новая пачка принята или отклонена с причиной;
2. обновлены признаки и v2-кэш, `/ready` показывает свежесть;
3. недельная очередь рассчитана и сохранена, включая корректный пустой ответ;
4. повтор расчёта не создаёт дубль по `recommendation_id`;
5. диспетчер сохранил решение и фактический исход;
6. устаревший кэш блокирует выдачу, старая очередь не показывается как новая;
7. после следующей пачки видны новая версия данных и история предыдущего
   расчёта.

ML принимает только то, что backend не исказил `target`, `target_version`,
`method`, окно, политику и статус `unknown`.

## Что остаётся за ML

Определение цели и проверка меток; версия модели и порог/суточный лимит;
переобучение на новых днях; честный временной бэктест с простым правилом;
разрешение или запрет каждой головы для пилота. Бэкендеру не нужно выбирать
метрику, переименовывать прокси в аварию или вручную подбирать порог по тесту.

## Фильтр готовности продукта

Команда использует [фильтр ML → продукт](ML_PRODUCT_GATE.md): после нескольких
временных проверок голова с рабочей precision ниже 50% откладывается, если
только не появилось новое действие, новая метка или новые данные. Для каждой
разрешённой головы backend хранит precision, recall, неизвестные исходы,
baseline, версию модели и статус `pilot`/`production_candidate`/`deferred`.
Исследовательские головы не должны автоматически попадать в заявки только
потому, что файл модели существует.
