## Что сдаём

В форме сдачи пять полей: репозиторий, документация (PDF), презентация (PDF), прототип (адрес стенда), доп. материалы (видео и бандл). Все пять ведут на один продукт — сайт диспетчера коллекторов.

Объекты заказчика устроены так: 1 район → 16 комплексов → 78 объектов → 11 485 каналов датчиков.

Что можно делать на сайте:

1. Войти под одной из пяти ролей: диспетчер ОДС, технический персонал, аналитик, руководитель подразделения, администратор. Смотреть дашборд, журналы и карточки могут все. Менять — по роли:
   - решение по прогнозу — диспетчер и администратор;
   - итог проверки — диспетчер, техник, аналитик и администратор;
   - создать, подтвердить или отменить заявку — диспетчер, руководитель и администратор;
   - перевести заявку в работу и закрыть — технический персонал и администратор;
   - загрузить журналы событий — аналитик и администратор;
   - настройки — только администратор.

   Каждое изменение записывается в журнал аудита. Полная матрица прав — `contracts/vocabularies.json`, ключ `permissions`.
2. Посмотреть прогнозы по трём сценариям:
   - **A_link** («Отказ датчика: риск потери связи») — канал датчика, который обычно передаёт данные, в ближайшие 24 часа, вероятно, не пришлёт ни одного показания за сутки;
   - **D** («Износ: плановая диагностика оборудования») — в ближайшие 7 суток вероятна тревога или плохое состояние насоса, вентилятора, ИБП, люка или датчика затопления. С 27.09 D считает не обученная модель, а правило «неисправности за неделю» (`n_bad_w7`): на проверке 2025 года модель молчала, правило ловило новые эпизоды (`ml/reports/RULE_VS_MODEL_RESULT.md`);
   - **недельная охранная очередь** («НСД: проверка объектов с хроническими охранными тревогами») — объекты, где охранные тревоги, скорее всего, продолжатся со 2-го по 8-й день после расчёта. Проникновение очередь не предсказывает. В интерфейсе её оценка подписана «относительный приоритет, не вероятность», а что это не прогноз проникновения, пишем в документации.
3. Открыть карточку прогноза: где, в какое окно времени, почему (факторы), что происходило на объекте за 30 дней.
4. Принять решение — «Выезд бригады», «Удалённая проверка / мониторинг», «Отложить» или «Отклонить» — с причиной из справочника. Без причины решение сохранить нельзя.
5. Вести заявку. Черновик по прогнозу создаёт ежедневный расчёт, заявку можно создать и вручную. Статусы: «Черновик» → «Подтверждена» → «В работе» → «Выполнена» или «Отменена». История каждого изменения сохраняется.
6. Увидеть в журнале прогнозов факт и итог проверки.
7. Смотреть ленту событий датчиков, которая обновляется сама, и получать уведомления.
8. Смотреть условную схему объектов. Координат заказчик не дал, поэтому объекты расставлены по пикетам, а не по карте, и на схеме это написано.

## Как устроен продукт

```
браузер ──> api (порт 8000) ──> ml (порт 8001, снаружи закрыт)
                 │
             PostgreSQL
```

- `frontend/` — сайт на React. Обращается только к `api`.
- `backend/` — это `api`: вход, роли, аудит, REST API, поток событий (SSE), ежедневный расчёт прогнозов. Он же раздаёт собранный сайт.
- `ml/` — ML-сервис. Считает прогнозы, когда `api` его вызывает, а `api` сохраняет их в БД. Сайт берёт прогнозы у `api` из БД и не ждёт, пока ML их посчитает.
- Модели и признаки лежат в бандле. Его подключает `compose.real.yaml`.

Контракты:

| Контракт | О чём | Где лежит |
|---|---|---|
| C1 | что ML-сервис отвечает backend | `ml/src/mkl/product_contract.py`, `contracts/ml_v1.schema.json` |
| C2 | REST API, который backend отдаёт сайту | `backend/app/schemas/`, `contracts/api_v1.openapi.json` |
| C3 | общие словари: действия, причины, статусы заявок, роли и права, подписи | `contracts/vocabularies.json` |
| C4 | что лежит в бандле и как он упакован | план, раздел 4 |
| C5 | как принимаются события датчиков и к какому классу относятся | план, раздел 4 |

## Как работать

**Поднять у себя.** Нужен Docker с Compose v2, данные заказчика не нужны.

```bash
cp .env.example .env
# вписать в .env DEMO_PASSWORD, SECRET_KEY, INTEGRATION_API_KEY: латиница, цифры, «-» и «_»
docker compose up --build -d --wait
python scripts/preload_demo.py
```

`--wait` ждёт, пока `db`, `ml` и `api` станут здоровыми: иначе `preload_demo.py` не сможет войти. Сайт — <http://localhost:8000>, Swagger — <http://localhost:8000/docs>. Логины: `dispatcher`, `technician`, `analyst`, `manager`, `admin`, пароль у всех — значение `DEMO_PASSWORD` из `.env`. Запуск без Docker описан в [README](../README.md), раздел «Режим разработки».

**Ветки и PR.**
- Ветка `feat/<ID>-<пара слов латиницей через дефис>` от свежего `main`, например `feat/BE-03-reference`.
- Префиксы коммитов: `feat`, `fix`, `test`, `docs`, `refactor`, `chore`.
- PR в `main` сливается, когда CI зелёный и есть одно ревью. Способ слияния — squash. В плане единственное исключение — PR каркаса (PM-05), он уже влит merge-коммитом. Если PM снова подтягивает `ml/` через `git subtree pull`, такой PR тоже сливаем merge-коммитом: squash теряет историю `ml/`.
- Force-push в `main` запрещён.
- Доска задач — GitHub Issues (PM-07). Статус своей задачи обновляет исполнитель.

**Кто кого ревьюит.**
- `ml/` — ML-1 и ML-2 друг друга.
- Клиент ML в backend и ежедневный расчёт (PM-09) — ML-1.
- Всё в `backend/` — BE, в том числе PR по ML2-01, ML2-03, ML1-11 и PM-09.
- Фронт — PM.

Ревьюер проверяет ещё две вещи: сложные места в коде прокомментированы (этого требует ТЗ §14), в диффе нет данных, паролей и `.env`.

**Заглушки.** Заменил заглушку — удали её шапку целиком: строку «ЗАГЛУШКА», строки «Заменить» и «Контракт». Проверка, названная в шапке, должна остаться зелёной: тест pytest, `npm run typecheck`, `scripts/smoke_compose.py` или `docker compose -f compose.yaml -f compose.real.yaml config`. В backend сигнатуры сервисов окончательные ([signatures.md](../backend/app/services/signatures.md)): меняем тела функций, а не их аргументы.

**Контракты.** Поменял схему, словарь или ответ заглушки — запусти `python scripts/export_contracts.py` и `cd frontend && npm run gen:api` и положи результат в тот же PR. Примеры ответов в `contracts/fixtures/` строятся из ответов backend и ML-заглушки, поэтому их меняет и правка тела функции. Если забыть, CI упадёт. С Сб 26.09 12:00 версия v1 заморожена: можно добавлять только необязательные поля и новые эндпоинты. Любой PR в контракт одобряют обе стороны — владелец и потребитель, а ломающее изменение ещё и согласуют с PM.

**Данные.** В git не кладём данные, модели, `.env` и пароли. Работаем в клоне без данных. `.gitignore` закрывает папки `data/`, `models/`, `Materials/` и файлы `.parquet`, `.pkl`, `.7z`, но не CSV и XLSX в других местах. `git add -A` рядом с ними добавит в коммит справочники и графики ППР, а репозиторий станет публичным.

**ML.** `mkl run` и `train_latest.py` без `--source-end` и `--out` перезаписывают `models/A_link.pkl` и `models/D.pkl` и портят модели демо-окна. На данных и моделях, которыми пользуются другие, запускать только после объявления в чате, на стенде — никогда.
