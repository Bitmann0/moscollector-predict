# Архитектура MVP

## Выбранное направление

«Отказ датчика». Этот вариант опирается на фактически предоставленные события и
справочник каналов. Категории пожара, доступа и износа добавляются как отдельные стратегии
прогнозирования после появления журналов подтверждения, допусков и реестра ремонтов.

## Поток данных

```text
CSV/XLSX или поток СМВУ
        ↓
валидация и нормализация
        ↓
агрегация признаков по каналу
        ↓
стратегия SensorFailureBaseline
        ↓
прогноз + факторы + рекомендация
        ↓
REST API → дашборд / заявка на ТО
```

Backend — модульный монолит на FastAPI. Аналитика выполняется Pandas/NumPy, заявки
хранятся в SQLite; переход на PostgreSQL не меняет внешний контракт. Frontend — лёгкое
статическое приложение без отдельной цепочки сборки, чтобы MVP запускался одной командой.

## Ограничения текущей модели

Предоставленный пример содержит события только за 1 августа 2026 года и не содержит
целевой метки «отказ в следующие 24 часа». Поэтому текущий `risk_score` — ранжирующий
эвристический baseline, а не доказанная вероятность. Сервис не скрывает это ограничение в
API и UI.

Для обучаемой модели потребуется:

1. связать события СМВУ с журналом неисправностей и ремонтами по каналу и времени;
2. исключить утечку будущего, разделив train/test по времени;
3. сформировать метку отказа на горизонте 24 часа;
4. обучить градиентный бустинг с class weights и откалибровать вероятность;
5. подобрать порог по условию Precision > 0,7, затем максимизировать Recall;
6. сохранить версию модели, датасета, порог и отчёт с confusion matrix.

## Следующие этапы

- потоковый ingest и дедупликация событий;
- PostgreSQL, миграции и фоновые задачи;
- реальные координаты объектов и географическая карта;
- журнал решений диспетчера как контур обратной связи;
- RBAC/LDAP, аудит действий, TLS и резервное копирование;
- мониторинг дрейфа данных и безопасное дообучение.
