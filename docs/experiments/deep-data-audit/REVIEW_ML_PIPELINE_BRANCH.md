# Проверка ветки `feat/ml-pipeline`

Проверена ветка `origin/feat/ml-pipeline` на коммите `60cdee9`. Это отдельная
история Git с корнем `ae90e0d`; общего предка с `main` нет. Прямое слияние заменит
текущий сервис отдельным ML-проектом и удалит приложение, документацию и CI основной
ветки. Полезные части нужно переносить выборочно с повторной проверкой.

## Что в ней полезно

- выделение эпизодов вместо подсчёта каждой записи как отдельного инцидента;
- walk-forward с временным разрывом между обучением и проверкой;
- отдельные показатели AP, базовой частоты, бюджета уведомлений и эпизодного Recall;
- робастные признаки числовых каналов, внутрисуточная телеметрия и профиль пропусков;
- сохранённые ответы экспертов. Из них следует, что нужно получить обновлённый
  справочник с прямым ID объекта, что журналы подтверждённых инцидентов не выдадут,
  а апрель–июнь 2021 относятся к миграции СМВУ и требуют отдельной обработки.

Эти идеи совпадают с направлением нашего плана: эпизодная цель, часовые числовые
признаки, несколько временных циклов и явный бюджет ложных уведомлений.

## P0. Удаляются неидентичные события

`mkl.ingest.build_events` применяет `DISTINCT ON (event_id)` отдельно внутри года.
`ид_события` не является уникальным ключом наблюдения. В нормализованном наборе после
удаления только точных дублей один ID соответствует нескольким различным строкам:

| Файл | Конфликтующих ID | Неидентичных строк, которые удаляет ветка |
|---|---:|---:|
| 2021 | 775 099 | 775 099 |
| 2022 | 667 317 | 667 317 |
| 2023 | 226 852 | 226 852 |
| Всего | 1 669 268 | 1 669 268 |

Поэтому ветка получает 311 312 808 событий вместо 312 982 076 событий после
проверяемой дедупликации. Оставлять одну произвольную строку по ID нельзя. Нужно
дедуплицировать по полному содержимому записи или заранее подтверждённому составному
ключу и отдельно учитывать `occurrences`.

## P0. «Объект» восстановлен неподтверждённым способом

`mkl.ingest.build_channels` вычисляет объект как первый компонент
`тег_инженерной_системы` до точки. В ответах экспертов прямо сказано, что исходной
связи не было и нужно скачать обновлённый справочник с отдельным ID объекта.
Имеющийся в нашей рабочей области справочник такого поля не содержит.

Ветка превращает префикс тега в 82 технические группы и затем называет их объектами.
Связь этих групп с 95 строками `справочник_объектов_диспетчер.csv` не доказана.
Поэтому результаты объектных голов `A_prime`, `B`, `C` и `E`, их локации и признаки
соседства нельзя принимать как проверенные объектные прогнозы. Префикс допустимо
исследовать как анонимную техническую группу, пока не получен обновлённый справочник.

## P0. Лучшая голова почти полностью прогнозирует молчание

Голова `A`, названная «Отказ датчика», использует выбранную метку `L5`: устойчивый
плохой эпизод `L6` плюс пропуск суток у ранее активного канала `L4`. В опубликованном
сравнении на одном validation-наборе:

- `L4` (только молчание): 108 170 положительных точек;
- `L5` (молчание плюс эпизод): 108 425;
- добавка зарегистрированных эпизодов: 255 точек, около 0,24% цели.

Заявленные Precision 0,700 и Recall 0,558 для `A` в основном относятся к прогнозу
отсутствия записи на следующий день. Это может быть полезной задачей контроля связи,
но не доказательством прогноза физического отказа. Её нужно назвать «риск потери
телеметрии» и оценивать отдельно от сигналов неисправности.

`A_prime` строится из одновременных плохих эпизодов внутри неподтверждённой группы.
В плохие состояния входят `Неопределен` и `Обесточен`; высокая предсказуемость может
отражать расписание обслуживания, потерю связи или пакетное логирование.

## P0. Отложенный период использован несколько раз

Первый коммит с финальной оценкой 2026H1 — `97456e6` от 15.09.2026 22:11.
После него добавлялись головы, телеметрия, внутрисуточные признаки, стекинг и настройки,
а `fd5b84e` от 16.09.2026 02:58 снова публикует улучшенный «финальный» замер на тех же
датах. В журнале экспериментов находится 23 записи `step=FINAL`.

Следовательно, 2026H1 перестал быть нетронутым holdout после первого просмотра.
Метрики остаются исследовательскими. Для следующего честного сравнения нужен новый
период либо заранее зафиксированный rolling backtest без ручной подгонки по его итогам.

Кроме того, последний коммит `391200d` от 19.09.2026 изменяет обучение: исключает
апрель–июнь 2021. `reports/final_metrics.csv` после этого не пересчитан; он создан
раньше, в `fd5b84e`. Поэтому отчёт на вершине ветки не соответствует текущему коду.

## P1. Порядок записей с одинаковым временем произволен

`mkl.states` и `mkl.panel` используют оконные функции `ORDER BY ts` без разрешения
ничьей. Несколько значений одного канала в одну секунду не имеют достоверного порядка.
От этого произвольного порядка зависят границы эпизодов, число переходов, интервалы,
дребезг и максимальный прогон одинакового значения.

Для насосов 99,76% секунд с «Неисправен» содержат и другое состояние, для вентиляторов
99,48%. На таких типах эпизодные признаки ветки нестабильны. Сначала нужно агрегировать
секунду в неупорядоченный набор состояний и явно определить переход между соседними
секундами либо исключить неоднозначные секунды в анализе чувствительности.

## P1. Дополнительные ограничения

- Путь `U:\hackathon` зашит в код, поэтому запуск не переносим без изменения исходников.
- Проект не содержит обновлённого справочника, моделей и фичестора; опубликованные
  метрики нельзя воспроизвести только из Git без локальных материалов автора.
- Цели пожара, проникновения, износа и подтопления остаются прокси-сигналами из той же
  телеметрии. Подтверждённых инцидентов, ремонтов и легитимности доступа нет.
- Ветки имеют разные корни Git. Сохранить сервис и ML-код можно только через выборочный
  перенос модулей и адаптацию к общей схеме данных.
