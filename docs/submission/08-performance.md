# Производительность и надёжность

Замеры сделаны 28.09.2026 на машине разработчика: Windows 11, Docker Desktop на WSL2, 16 логических процессоров, 32 ГБ оперативной памяти. Стек — `compose.yaml` + `compose.real.yaml`, ML работает в режиме `real` на бандле из данных заказчика (`bundle-20260928-3`: модели A_link с рабочей точкой 0,70). В базе лежит история журнала СМВУ за 02.05–29.06.2026 (10 277 666 событий) и прогнозы демо-окна после `scripts/preload_demo.py`. Сырые результаты — в `docs/submission/perf/`, команды повторения — в конце раздела.

На ВМ стенда (4 vCPU, 16 ГБ, без GPU — решение D9) замеров нет, оборудование заказчика не известно. Числа ниже — оценка на одной машине, а не гарантия для другой.

| Восстановление после сбоя | не более 4 ч | `pg_restore` в чистый PostgreSQL 16 — 133–309 с | там же |

## Расчёт прогноза

Прогноз считает ML-сервис (`ml/src/mkl/product_api.py`, `POST /api/v1/score`). Один вызов обрабатывает сутки целиком: все каналы по голове A_link и всё оборудование по голове D. Ответ содержит все оценённые алерты с отметкой лимита `in_budget`, вклады признаков, покрытие и черновики заявок: 02.06 — 2 992 алерта. Поэтому время одного объекта не больше времени суток.

`scripts/measure_ml.py` шлёт запросы из контейнера api по одному, как `run_daily`: за каждый день 01.06–30.06, с факторами и пустым журналом выданного, `history_complete_from` — за 7 суток до дня расчёта (`docs/submission/perf/ml_score_june.jsonl`).

| Вызов | Число вызовов | Минимум | Медиана | Максимум |
|---|---:|---:|---:|---:|
| `POST /api/v1/score`, A_link и D | 30 | 0,14 с | 7,61 с | 10,57 с |
| `GET /api/v1/guard-weekly-inspections`, понедельники | 5 | 0,05 с | 0,22 с | 0,23 с |

- 0,14 с — это 01.06: событий за этот день в журнале нет, сервис сразу отвечает `no_data`.
- По понедельникам (01, 08, 15, 22 и 29.06) в файле есть только строка недельной очереди: скрипт печатает последнюю строку дня, и строка `/score` в вывод не попала. В итоговую строку `summary` все 30 вызовов вошли.
- Во время первого прогона на той же машине параллельно работали агенты сборки, и `/score` дал медиану 9,32 с при максимуме 13,9 с (`docs/submission/perf/ml_score_june_loaded.jsonl`). Этот прогон в таблицу не входит.
- Пик памяти контейнера ML по `docker stats` с шагом 2 с — 966 МиБ, в первом прогоне (`docs/submission/perf/ml_docker_stats_loaded.txt`); лимит в `compose.stand.yaml` — 6 ГБ.
- Факторы: у алертов в бюджете в ответах `/score` за 02–30.06 — 781 фактор (A_link 775, D 6), без русской подписи 0 (`docs/submission/perf/factor_labels_june.txt`). В журнале после прелоада — 688 факторов, без подписи тоже 0 (`docs/submission/perf/journal_counts_0928.txt`).

Суточный расчёт в backend (`POST /api/v1/admin/run-daily`) вызывает `/score`, при необходимости недельную очередь и `/outcomes`, после чего пишет прогнозы, журнал выданного, черновики заявок и уведомления. На каждый день демо-окна у `preload_demo.py` уходит 9,2–25,0 с, на 01.06 без данных — 2,0 с. Предзаполнение целиком занимает 417 с без ошибок: недельная очередь за 21 понедельник до окна (0,3–0,7 с каждый), 29 суточных расчётов и эмуляция решений (`docs/submission/perf/preload_demo_0928.txt`). После него в журнале 154 прогноза в бюджете и 65 заявок (`docs/submission/perf/journal_counts_0928.txt`).

Признаки нового дня берутся из предрасчитанного фичестора бандла. Инкрементального расчёта признаков нет: полный пересчёт суточной панели на машине разработки занял 4 949 с (`ml/docs/EVALUATION_AND_RUNTIME.md`). Поэтому свежие данные в продукте появляются пересборкой бандла (раздел 06), а не потоком. Это ограничение решения, оно названо и в разделе 03.

## Поток событий

Поток СМВУ эмулирует проигрыватель `scripts/replay.py`. Он отдаёт события 30.06.2026 в темпе их регистрации, пачками раз в 5 с, через `POST /api/v1/ingest/events` с ключом роли `integration`. API проверяет строки, снимает дубли по хешу полного кортежа, классифицирует событие (C5), пишет его в PostgreSQL и для тревог создаёт уведомление в SSE.

Прогон шёл одновременно с нагрузочным тестом. Проигрыватель запущен с `--align-to-clock --catch-up`. Сначала одной серией ушли события 00:00–17:15: 149 140 строк за 46 с. Дальше шёл живой поток (`docs/submission/perf/replay_latency_0630.csv`). В таблице — первые 120 живых пачек, 10 минут; в файле их 123: ещё три проигрыватель успел отправить до остановки.

| Показатель | Значение |
|---|---|
| Живых пачек | 120, в них 1 495 событий |
| Задержка «событие пришло по темпу → ответ API после записи в БД», медиана по пачкам | 4,8 с |
| То же, p95 | 5,1 с |
| То же, максимум без первой пачки | 6,4 с |
| Первая живая пачка | 45,8 с: в неё попали события, пришедшие за 46 с догрузки |
| Время запроса на пачку, медиана и максимум | 0,046 с и 1,72 с |

Задержку почти целиком даёт интервал отправки пачек, `--interval 5`.

Загрузка истории (`scripts/replay.py --bulk`, события без уведомлений) за 02.05–29.06.2026 — 10 277 666 строк за 2 684 с, 3 829 строк в секунду, без ошибок.

## Нагрузка

Профиль — `scripts/load_test/locustfile.py`:
- 20 пользователей в пропорции 8 : 5 : 4 : 3 — диспетчеры, технический персонал, аналитики, руководители;
- каждый входит через `POST /api/v1/auth/login` и держит открытым поток `/api/v1/stream`, как вкладка браузера;
- набор запросов свой у каждой роли; сценарий только читает.

Прогон длился 10 минут, одновременно шёл поток событий (`docs/submission/perf/locust_20users_10m_stats.csv`).

| Запрос | Запросов | Медиана | p95 | p99 | Максимум |
|---|---:|---:|---:|---:|---:|
| `GET /api/v1/forecasts` | 862 | 66 мс | 200 мс | 260 мс | 430 мс |
| `GET /api/v1/forecasts/{id}` | 625 | 23 мс | 110 мс | 240 мс | 350 мс |
| `GET /api/v1/work-orders` | 610 | 12 мс | 61 мс | 140 мс | 350 мс |
| `GET /api/v1/events` | 561 | 360 мс | 560 мс | 770 мс | 3 027 мс |
| `GET /api/v1/dashboard/summary` | 527 | 110 мс | 270 мс | 400 мс | 660 мс |
| `GET /api/v1/system/status` | 223 | 140 мс | 320 мс | 1 800 мс | 2 320 мс |
| Все запросы | 4 339 | 64 мс | 400 мс | 540 мс | 3 027 мс |

- Пропускная способность — 7,2 запроса в секунду.
- Все 20 потоков SSE получили первое сообщение в среднем за 24 мс.
- Самый тяжёлый запрос — журнал событий: API считает число строк по 10,28 млн событий с фильтром штатного газа.
- `/system/status` на каждый вызов спрашивает ML `/ready`, отсюда хвост до 2,3 с.

Одна ошибка из 4 339 — `RemoteDisconnected` на `GET /api/v1/work-orders/{id}`. Uvicorn по умолчанию закрывает простаивающее соединение через 5 с, а клиент успел отправить запрос в уже закрытое. После прогона api держит соединение 75 с (`backend/entrypoint.sh`), Caddy на стенде переиспользует его не дольше 60 с (`deploy/Caddyfile`). Повторного прогона с этой правкой не было.

## Надёжность

- **Перезапуск.** У сервисов `db`, `ml`, `api` в `compose.yaml` стоит `restart: unless-stopped` и проверки здоровья: `pg_isready` для БД раз в 5 с, `/health` для ML раз в 10 с. api стартует только после того, как `db` и `ml` прошли проверку здоровья. Стенд (`compose.stand.yaml`) добавляет лимиты памяти (ml 6 ГБ, db 3 ГБ, api 2 ГБ, replay 1 ГБ, backup 512 МБ, caddy 256 МБ) и ротацию журналов контейнеров: 10 МБ × 5 файлов.
- **Отказ ML.** Статус каждой головы суточного расчёта пишется в `forecast_runs`. Строка статуса интерфейса показывает, на связи ли ML (`frontend/src/components/Layout.tsx`). Уже записанные прогнозы и журналы читаются из PostgreSQL без обращения к ML (раздел 05).
- **Резервное копирование.** Сервис `backup` раз в сутки пишет `pg_dump -Fc` в `./state/backups/` и хранит 7 последних копий. Процедура восстановления — `README.md`, раздел «Стенд».

| Шаг | Замер |
|---|---|
| `pg_dump -Fc` рабочей базы | 74 с, файл 521 МБ |
| `pg_restore` в чистый postgres:16 без нагрузки | 133 с |
| То же, пока в исходной базе шёл подсчёт строк | 309 с |
| Счётчики после восстановления | `events` 10 277 666, `forecasts` 55 942, `decisions` 338, `work_orders` 222, `outcomes` 475, `audit_log` 2 145 |

Дамп снят в ночь на 28.09, до перехода на модели 0,70: в базе был прелоад на моделях A_link 0,50, поэтому заявок в ней 222, а не 65. Столько же событий дала загрузка истории, столько же заявок — тот прелоад. Сырые логи — `docs/submission/perf/backup_restore_0928.txt`.

Время восстановления работоспособности складывается из пересоздания контейнеров (пересборка образов из кэша — 19–27 с в наших прогонах) и `pg_restore`. На этой машине это единицы минут при нормативе 4 часа.

## Обучение моделей

Обучение в продукт не входит: модели приходят в бандле, дообучение — отдельная команда (раздел 04).

- Одна датированная модель A_link (`ml/scripts/train_latest.py --source-end`, LightGBM на CPU) обучается 185–193 с.
- В эксперименте с ансамблем обучение одной модели на окне заняло: LightGBM на CPU 60–114 с, XGBoost 57–82 с и CatBoost 33–39 с на GPU RTX 3060 Ti (`ml/reports/A_LINK_ENSEMBLE.md`).
- Сервис ML в контейнере считает на CPU, GPU ему не нужен.

## Как повторить

Из корня репозитория при запущенном стеке:

```bash
docker compose -f compose.yaml -f compose.real.yaml exec -T api python - < scripts/measure_ml.py
pip install locust
mkdir -p data/load_test
locust -f scripts/load_test/locustfile.py --host http://127.0.0.1:8000 --users 20 --spawn-rate 2 --run-time 10m --headless --csv data/load_test/run
python scripts/replay.py --day 2026-06-30 --align-to-clock --catch-up --latency-log state/replay_latency.csv
```

Нагрузочный прогон 28.09 шёл против порта 8010 локальной сборки. `DEMO_PASSWORD` locust берёт из `.env`. Команды счёта журнала и подписей факторов — в шапках `docs/submission/perf/journal_counts_0928.txt` и `factor_labels_june.txt`.
