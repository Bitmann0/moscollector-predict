## Подтверждённые расхождения

### 1. L9c имеет переменную задержку появления метки

В [labels.py](../src/mkl/labels.py) длина разрыва определяется следующим
сообщением, а событие датируется первым пропущенным днём. Старые скрипты
строят метки по полной истории и затем режут их по дате прогноза. Запас
`horizon_days + 1` не гарантирует, что следующий отчёт канала уже поступил.

Контрпример: канал отчитывается 1–8 января и возвращается 20 января.
В полной истории 8 января получает `y=1`; на 10 января исход по контракту
L9c ещё unknown. Следовательно, такая строка может внести будущую информацию
в обучение, калибровку или выбор порога. Удаление только последней строки
канала во всей выгрузке эту проблему не закрывает.

В независимом оценщике хранится `available_on=next_report_day`. Обучение,
калибровка и отбор порога получают собственные срезы доступности. Unknown
исключается из supervised fitting, но остаётся среди кандидатов выдачи.
Тест с добавлением будущих наблюдений проверяет неизменность старого среза.

### 2. D превращает отсутствие будущей телеметрии в отрицательный исход

`_observable(7)` проверяет общий конец выгрузки, а не наблюдаемость каждого
канала. `_emit` ставит ноль, если не нашёл события. Если один канал исчез
1 января, а другой отчитывается до 11 января, первый получает отрицательную
семидневную метку. Поэтому `unknown=0` в прежних окнах не доказывает
полноту наблюдений. Inner join перед ранжированием также исключает
неразмеченных кандидатов при появлении таких строк.

Проверка вводит явно версионированный **D_observed_v1**: записанный позитив
остаётся позитивом; отрицательный исход подтверждается только при наличии
телеметрии с заполненными счётчиками во все семь будущих суток. Иначе —
unknown. Это консервативный контракт наблюдаемости для чувствительности
результата; его необходимо согласовать с владельцем данных, поскольку
журнал может содержать события изменения состояния, а не heartbeat.
Такую метку нельзя молча назвать прежней D. Для длительности эпизода
используется дата последнего наблюдения, образовавшего `dur_s`, а не просто
прибавление часа к его началу.

### 3. Порог подбирается без cooldown

[daily_target_operating_point](../src/mkl/metrics.py) учитывает дневной top-k
и ничьи, но не журнал выдачи. Оба оценщика и `train_latest.py` используют
именно его. Итоговый бэктест затем добавляет cooldown.

Контрпример: один и тот же канал восемь дней имеет риск 0,9; первый исход
отрицательный, остальные семь положительные. Старый отбор видит 7/8 = 87,5%
и восемь рекомендаций. Полная политика выдаёт одну отрицательную
рекомендацию и подавляет остальные семь. Не соблюдается ни точность,
ни минимальный размер выдачи после паузы.

Новый отбор перебирает достижимые пороги и каждый раз воспроизводит выдачу
целиком. Приоритет: максимум известных попаданий, затем precision, затем
более высокий порог. Unknown входит в знаменатель нижней границы precision.

### 4. «Нет порога» не всегда означает воздержание baseline

Старый A_link оценщик заменяет не найденный порог на `nextafter(max(past), inf)`.
Для некалиброванного правила `gap_vs_own_rhythm` будущие значения могут
превысить прошлый максимум. В сохранённом JSON уже есть такой случай:
06.04–04.07.2025, baseline при минимуме 70%, `feasible=false`, **27 алертов**.
Аналогичный путь есть у порогового baseline D, хотя его сохранённые окна
не демонстрируют выдачи при не найденном пороге.

В независимом расчёте воздержание — отдельное состояние `threshold=null`,
которое всегда даёт пустую выдачу. Безусловный top-k — отдельная политика.

### 5. Эпизодная метрика сдвигает окно второй раз

`episodes_per_100_alerts` ищет начало положительного ряда **уже будущей**
метки `y(day)`, а затем ещё раз смотрит назад на горизонт. Алерт 1 января
может быть засчитан для события 3 января при горизонте один день, если
положительная метка начинается 2 января. Этот контрпример воспроизводится
тестом.

В A_link отчёте во всех пяти окнах пойманных эпизодов больше, чем верных
алертов: суммарно **5 815 против 5 024**. При этой суточной постановке одному
прогнозу соответствует максимум один новый разрыв своего канала.
Поэтому заявленные 5,0% эпизодного охвата нельзя принимать как проверенные.
Это не исправляется простым пересчётом процентов по старому JSON: нужен
матчинг с исходными датами событий.

Новая метрика связывает рекомендацию с реальным началом в `(asof, asof+H]`.
Для D наблюдаемый нормальный день разделяет эпизоды; пропущенные дни сами
по себе новый эпизод не создают. Начало без нормального наблюдения за
предыдущие сутки помечается неопределённым. Отдельно считаются уникальные
начала, повторные рекомендации и уже продолжающиеся случаи. Один алерт D
может покрыть несколько новых эпизодов, поэтому эти категории не обязаны
суммироваться в число рекомендаций.

### 6. Прежний 90-дневный бэктест не воспроизводит обновление сервиса

Сервис ограничивает возраст конца порогового окна 8 сутками для A_link
и 14 для D. В старых бэктестах модель и порог заморожены на 90 суток:
большая часть оценённой выдачи не прошла бы эту проверку сервиса.
Кроме того, `validate_pilot_artifact` проверяет только положительный лаг,
но принимает D с концом порогового окна вчера, хотя семидневная метка
ещё не могла полностью созреть. Это отдельно воспроизведено тестом.

Новый расчёт обновляет модель, калибровку и порог каждые семь дней;
журнал рекомендаций переносится через обновления и границы отчётных окон.
Первая тестовая дата — явный запуск с пустым журналом. Каждый ретроспективный
30-дневный блок подбора порога также имеет явно указанный пустой начальный
журнал; это допущение следует проверить на реальной истории выдачи.

## Воспроизведение

CPU-окружение:

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install -e '.[dev,api,schedules]'
./.venv/bin/python -m pytest tests/test_second_ml_audit.py -q
./.venv/bin/python scripts/audit_second_ml.py --mode preflight
```

После получения готовых файлов структура каталога должна быть такой:

```text
data/
  interim/daily_channel.parquet
  interim/episodes.parquet
  interim/channels.parquet
  features/sensor.parquet
```

```bash
./.venv/bin/python scripts/audit_second_ml.py \
  --mode historical --data-root /path/to/data \
  --splits 5 --test-days 90 --refresh-days 7 --threads 4 \
  --output reports/second_ml_historical.json
```

Без файлов historical-режим завершается кодом 2 и записывает
`blocked_missing_data`, `historical_metrics=null`. Он не подставляет
старые или искусственные метрики. При наличии данных создаёт JSON и
Markdown-таблицу рядом: пороги каждой недели, известные/unknown исходы,
месячную и дневную выдачу, каналы вне текущего справочника, эпизоды,
CPU/wall-time обучения, скоринга и политики, peak RSS, версии библиотек
и SHA-256 входов и кода. Файлы моделей не публикуются и не заменяются.

Полный исторический прогон включает около 130 обучений на CPU. Перед ним
нужно проверить версию и происхождение готовых признаков: этот скрипт
проверяет доступность меток, но не доказывает отсутствие утечки внутри
предварительно рассчитанного фичестора или текущего справочника. После
получения исходных журналов требуется проверка признаков на усечённой
истории. Отсутствие рекомендаций вне покрытия не означает отсутствие риска.

## Фактически выполненные проверки

- 21 новый тест: контрпримеры, сохранение unknown в бюджете, совпадение
  ранжирования с сервисом, пауза на границе 7/8 суток, одинаковые риски,
  отсутствие добора, перенос журнала, еженедельные обновления обеих голов
  и сквозной прогон от искусственных parquet до JSON/Markdown.
- Итоговый прогон доступной части репозитория: **571 passed, 3 deselected**,
  7,27 секунды. До исключения трёх проверок они были запущены и завершились
  ошибками именно из-за отсутствующих данных: `test_paths_exist`,
  `test_attach_events_exposes_expected_columns`,
  `test_real_reference_has_a_name_for_every_object`. Их код не изменялся.
- Preflight записывает отсутствие всех четырёх входов. Historical-режим
  без данных проверен отдельно: код завершения 2, исторические метрики null.
- Среда проверки: macOS arm64, Python 3.13.3, DuckDB 1.5.5,
  Polars 1.44.2, NumPy 2.5.3, LightGBM 4.7.0, scikit-learn 1.9.1,
  pytest 9.1.1. Есть одно предупреждение стороннего FastAPI/Starlette о
  будущем изменении тестового HTTP-клиента; ошибки расчётного контура нет.

Время тестов на искусственных примерах не является замером CPU-инференса
на данных заказчика и не подтверждает норматив 300 секунд.

## Решение по головам

| Голова | Решение независимой проверки сейчас | Человеческая подпись после успешной проверки |
|---|---|---|
| A_link | Оставить исследовательской до пересчёта с доступностью L9c и полной политикой | «Рекомендация: удалённая диагностика связи; возможное начало необычного пропуска телеметрии завтра» |
| D | Оставить исследовательской до согласования наблюдаемости и пересчёта новых эпизодов | «Рекомендация: плановая диагностика оборудования; возможный сигнал тревоги/неисправности в следующие 7 суток» |

Это вывод аудитора, а не изменение текущего `product_status` исходной ветки.
Критерии 50% и 70% показаны раздельно: 70% — прежний критерий выбора D,
50% — командный минимум обсуждения пилота. При следующем прогоне нужны
устойчивое качество полной политики по окнам, преимущество над сопоставимым
правилом, достаточная реальная выдача и приемлемая нагрузка диспетчера.
Автоматические выездные заявки по одной ML-оценке не допускаются.
