## Постановка

Метка — первое числовое показание вне [3, 40] °C в окне `[as_of, as_of + 24 ч)` после 24 или 72 часов без такого показания. `as_of` — местная полночь. Признаки берут только записи до `as_of`: окна 6, 24, 72, 168 и 720 часов, первое и последнее значение, минимум, максимум, среднее, разброс, наклон, плотность записей, расстояние до границ, медиана и IQR за 30 суток, день недели и года. ID канала в признаки не входит. Несколько значений в одной секунде сворачиваются как неупорядоченное множество (min, max, mean): порядка между ними источник не даёт.

Границы 3 и 40 °C взяты из текстовых состояний того же датчика: «Температура ниже 3ºC» и «Температура выше 40ºC» у типа «Датчик температуры» (`analysis/annual_profiles.json`, например строка 2779: 2019 год, `alarm=true`, 168 записей). Второе состояние входит в `FIRE_STATES` (`ml/src/mkl/config.py:40`). Владелец данных эти границы не подтверждал.

Правдоподобными считаются значения в [-60, 150] °C — это `VALUE_LIMITS["Датчик температуры"]` (`config.py:114`); -3276 и 999 там описаны как аппаратные переполнения. Апрель–июнь 2021 исключён до построения признаков (`EXCLUDED_PERIODS`, `config.py:89`).

Строка попадает в оценку, только если завтра у канала есть числовые записи в объёме не меньше 25% его недельного ритма. Так отброшено 149 958 канало-суток (`quality.excluded_unknown_or_low_future_cadence`). Значит, метрики условны по наличию завтрашних данных: в сервисе алерт на канал, который завтра замолчит, стал бы `unknown`, а не попаданием.

## Данные

По `temperature_episode_sources.json`: 600 температурных каналов, 1 363 583 записи после дедупликации по содержанию (канал, момент, тревожность, значение), из них 1 020 004 числовых в [-60, 150] °C, 1 446 299 канало-суток с 2019-01-02 по 2026-06-30.

`catalog_sha256` в манифесте (`fa550d4c…`) — хеш прежнего справочника каналов. У текущего хеш `87b3230e…` (`analysis/UPDATED_CATALOG_AUDIT_2026-09-24.md`); по тому же аудиту ID и типы каналов в новой версии не менялись.

## Протокол

В каждом фолде сравниваются логистическая регрессия с `class_weight="balanced"`, `HistGradientBoostingClassifier` и правило без обучения «расстояние до границы плюс модуль суточного тренда». Модель выбирается по AP на validation, порог — на threshold, тест — следующее полугодие. Порог: наибольшая полнота при precision > 0,7 и не меньше 10 алертах, а если такого нет — максимум F0.5.

| Фолд | train | validation | threshold | test |
|---|---|---|---|---|
| test-2024h1 | 2019-02-01 … 2023-01-01 | 2023-01-01 … 2023-07-01 | 2023-07-01 … 2024-01-01 | 2024-01-01 … 2024-07-01 |
| test-2025h1 | 2019-02-01 … 2024-01-01 | 2024-01-01 … 2024-07-01 | 2024-07-01 … 2025-01-01 | 2025-01-01 … 2025-07-01 |
| test-2026h1 | 2019-02-01 … 2025-01-01 | 2025-01-01 … 2025-07-01 | 2025-07-01 … 2026-01-01 | 2026-01-01 … 2026-07-01 |

Правая граница не включается. Периоды идут встык. Утечки метки нет: строка входит в период, только если её метка заканчивается внутри него. Но протокол mkl держит зазор `EMBARGO_DAYS = 31` (`config.py:101`), а здесь 720-часовые признаки первых суток validation видят записи, из которых собраны метки последних суток train. Перенесённый скрипт считает третий протокол `temporal_all_channels_embargo31`: те же тестовые полугодия, концы train, validation и threshold сдвинуты на 31 сутки раньше. В JSON из PR его нет.

Тест 2026H1 совпадает с отложенным периодом mkl (`HOLDOUT_START..HOLDOUT_END`, `config.py:97`), который до этого просматривали 38 раз (`holdout_uses.md`). Числа 2026H1 здесь ретроспективные, не отложенные.

## Рабочая точка

Условие «precision > 0,7 при не меньше 10 алертах» на периоде threshold не выполнено ни в одном из 12 прогонов (2 окна × 2 протокола × 3 фолда): везде `threshold_rule = fallback_f0.5_precision_constraint_unmet`.

При лимите диспетчера 3 алерта в сутки (`test_ranking.daily_budget_3`, окно 24 ч):

| Тест | Алертов | Суток | Precision | Recall | Precision при 1 алерте в сутки |
|---|---:|---:|---:|---:|---:|
| 2024H1 | 536 | 179 | 0,101 | 0,432 | 0,123 |
| 2025H1 | 543 | 181 | 0,088 | 0,393 | 0,094 |
| 2026H1 | 537 | 179 | 0,106 | 0,452 | 0,151 |

Вывод из этих же чисел: позитивов в тесте 122–126, алертов 536–543, поэтому precision при таком лимите не выше 126 / 537 = 0,235 при любой модели. Эпизодов меньше, чем мест в очереди.

## Каналы, не виденные при обучении

20% каналов (корзина 0 по SHA-256 от ID, `channel_bucket`) убраны из train и используются только в validation, threshold и test.

| Окно | Precision | Recall | AP | Позитивов в тестах |
|---|---:|---:|---:|---|
| 24 ч | 0,257 | 0,335 | 0,230 | 20 / 25 / 24 |
| 72 ч | 0,542 | 0,340 | 0,347 | 16 / 23 / 22 |

Среднее 0,542 держится на фолде 2026H1: precision 1,0 на 8 алертах. При 16–23 позитивах на тест такое число неустойчиво и рабочей оценкой быть не может.

## Аудит метки

По `temperature_episode_target_audit.json`:

- 3 415 из 3 594 начал эпизодов, разделённых 72 часами (95,0%), состоят из ровно 0, 1 или 2 °C. Ещё 55 начал — другие значения ниже 3 °C, 124 — выше 40 °C.
- Ни одна из 27 747 записей вне диапазона (398 каналов) не помечена `alarm=true`.
- В 1 621 из 27 546 «плохих» секунд есть и значение внутри диапазона.
- 1 338 положительных канало-суток при окне 72 ч приходятся на 292 канала; на 10 самых частых — 14,8%.

Генератора этих чисел в PR нет. `target_audit` в перенесённом модуле восстанавливает определения по описанию из README PR (docstring функции), поэтому при перезапуске счётчики могут не совпасть с эталоном.

Физический смысл точных 0/1/2 °C и самих границ владелец не подтверждал, поэтому сценарий называется прогнозом выхода показания за условный диапазон, а не поломки датчика.

## Перезапуск

Нужен полный журнал 2019–2026: в бандле из событий есть только `data/interim/events_year=2026.parquet` (`ml/scripts/build_bundle.py`, `REQUIRED`), а фолды начинаются с 2019-го. Сколько идёт прогон, неизвестно: в PR время не записано.

```powershell
cd ml
python -m mkl.cli run ingest              # если data/interim ещё не собран
python scripts/exp_temperature_episode.py features
python scripts/exp_temperature_episode.py backtest --clean-hours 24
python scripts/exp_temperature_episode.py backtest --clean-hours 72
python scripts/exp_temperature_episode.py audit
python scripts/holdout_uses.py
git diff reports/temperature_episode_*.json
```

`features` и `audit` принимают `--events` (шаблон parquet событий, если они лежат не в `data/interim`), `features` — ещё `--raw-dir` и `--catalog` для хешей манифеста. Признаки пишутся в `data/features/temperature_episode_hourly.parquet`, в git не попадают. `backtest` после записи отчёта добавляет в `experiments/log.jsonl` запись `step=FINAL` на каждый посчитанный фолд 2026H1, по одной на протокол. `holdout_uses.py` склеивает записи одной минуты и одного коммита в один просмотр. Записи идут подряд, поэтому прогон — это один новый просмотр отложенного периода; два он даст, только если запись придётся на смену минуты.

Эталон для сверки: 1 363 583 записи, 600 каналов, 1 446 299 канало-суток, 191 170 и 189 598 строк в оценке, средние precision 0,354 и 0,336. Расхождение ожидаемо: хранилище PR #4 брало только строки, где `тревожное` — одно из t/true/1/f/false/0, `ид_события` > 0, а дата и время разбираются по `%Y-%m-%d %H:%M:%S` (`backend/app/ingest.py:64-74` в ветке `feature/annual-ingestion`, коммит `f6c6fbe`). Приём mkl строк по `тревожное` не отбрасывает, тревожными считает только t/true, а от `ид_события` требует лишь, чтобы он разбирался как целое (`ml/src/mkl/ingest.py`, `build_events`). Если числа изменятся, их надо обновить одновременно здесь, в плане сдачи (`docs/superpowers/plans/2026-09-25-team-plan-to-submission.md`, §11), в `ML_PRODUCTION_STATUS.md`, `analysis/MULTI_HEAD_ML_STRATEGY.md` и `ml/docs/ML_BACKEND_HANDOFF.md`.
