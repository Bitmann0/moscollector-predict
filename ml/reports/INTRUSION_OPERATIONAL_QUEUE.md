# C: полная очередь прогноза на следующие сутки

25.09.2026. Здесь проверена версия задачи, которую может выполнить сервис:
список кандидатов выбирается **до** наступления завтрашнего дня. Результат
остаётся ретроспективным и относится к записанному сигналу СМВУ при охране
в момент сигнала, не к подтверждённому проникновению.

## Где предыдущая проверка была слишком удобной

[Предыдущий опыт](INTRUSION_EVENT_TIME.md) оставлял для теста только строки,
у которых завтра есть телеметрия и можно решить, была ли тревога. Диспетчер
не знает этого заранее. Поэтому предыдущие 24,8% при четырёх предупреждениях
нельзя сразу считать качеством рабочей выдачи.

Теперь кандидат берётся по данным **сегодня**: у объекта есть строка
признаков на конец дня, последнее известное охранное состояние — «на охране»,
а сообщение о состоянии не старше семи суток. Это около 31 объекта в день
на тестовых периодах. Ограничение свежести было выбрано после знакомства
с данными, так что результаты нельзя называть слепой проверкой.

Завтрашний исход положителен, если в журнале записан сигнал из
`INTRUSION_STATES` с `alarm=true` при охране в момент сигнала. Отрицательный
исход ставится лишь тогда, когда завтра есть строка телеметрии объекта и
нет сигнала с неопределённым охранным состоянием. Остальные исходы
**неизвестны**. Положительный сигнал считается наблюдаемым сам по себе.
Наличие строки объекта — слабая проверка наблюдаемости: она не подтверждает,
что каждый охранный датчик работал исправно. Поэтому доля записанных
попаданий — качество именно имеющегося журнала, не оценка реальных проходов.

## Протокол

Те же три следующих друг за другом 90-дневных тестовых периода 2025 года,
2025-04-05 … 2025-12-30. Для каждого: обучение на более ранних датах,
31 день разрыва, 60 дней контроля, ещё 31 день разрыва до теста.
Порог не подбирался: сравнивается фиксированный бюджет один или четыре
объекта в каждые сутки. Обучение модели «при известном исходе» использует
только известные строки; вариант «записанная тревога» обучается на всей
очереди и рассматривает неизвестный исход как отсутствие *записи*.
Модель совместного ранжирования умножает две оценки: риск тревоги при
наблюдаемом исходе и вероятность известного исхода. Эти числа используются
только для порядка выдачи, без заявления о калиброванной вероятности.

В тесте **8 429** текущих кандидатов, **7 723** известных исхода и
**596** записанных положительных событий. Известность/неизвестность
проверяется после прогноза; все кандидаты остаются в очереди.

## Общая очередь: до четырёх предупреждений в день

| Ранжирование | Записано попаданий / 1 080 предупреждений | Доля | Исход неизвестен |
|---|---:|---:|---:|
| Правило: число точных тревог за неделю | 223 | 20,65% | 68 |
| Уточнённое правило: неделя, затем месяц, затем давность | 237 | 21,94% | 66 |
| LightGBM, простые признаки истории | 221 | 20,46% | 84 |
| LightGBM, расширенная история; обучение на известных исходах | 228 | 21,11% | 84 |
| LightGBM, прогноз будущей **записанной** тревоги | **243** | **22,50%** | 49 |
| Две модели: тревога × известность исхода | 237 | 21,94% | **31** |

Лучший вариант нашёл 88, 94 и 61 событие по трём периодам. У уточнённого
простого правила 237 попаданий, разница всего **шесть** на 1 080
предупреждений (+0,56 процентного пункта). Парный bootstrap по дням
внутри каждого квартала, 5 000 повторений: 95% интервал разницы
**−0,83 … +2,04 п.п.** при 14-дневных блоках и
**−0,46 … +1,48 п.п.** при 30-дневных. Надёжного преимущества
сложной модели над простым правилом не получили.

При **одном** предупреждении в день простое недельное правило нашло
94 из 270, лучший LightGBM — 82 из 270. Уточнённое правило — 88 из 270.
Результат сильно зависит от бюджета; нельзя выбрать лучший бюджет по
этим тестовым ответам и объявить его независимой оценкой.

## Первые сигналы после спокойной недели

Отдельная очередь: семь наблюдаемых календарных дней без известной или
неопределённой охранной тревоги. Здесь **3 967** кандидатов, **158**
будущих записанных первых сигналов. При четырёх предупреждениях ежедневно:

| Ранжирование | Записано попаданий / 1 080 | Доля |
|---|---:|---:|
| Недельный счётчик (для тихой очереди постоянен) | 46 | 4,26% |
| Уточнённое простое правило | **77** | **7,13%** |
| LightGBM для записанной тревоги | 73 | 6,76% |
| LightGBM, простые признаки истории | 73 | 6,76% |

Уточнённое правило выигрывает у лучшей общей модели на четыре попадания;
30-дневный bootstrap интервал разницы модели с правилом
**−1,48 … +0,83 п.п.** Польза ML для начала эпизода не доказана.
Доля около 7% остаётся слишком низкой для автоматической заявки на выезд.

## Что стало частью воспроизводимого ML-пайплайна

Добавлен отдельный строитель **v2-разметки**: получает исходные события,
сопоставляет тревогу с последним охранным сообщением **до её времени**,
оставляет неизвестными одновременные противоречивые изменения и
неподтверждённые отрицательные исходы. Конечную дату берёт из последней
наблюдаемой даты объектного фичестора; при поступлении новых дней диапазон
можно продлить без правки SQL. В текущем запуске: 2023-01-01 … 2026-06-29,
63 637 строк меток, 55 572 известных исхода, 2 785 положительных.

Проверки согласованности: за 2023–2025 годы v2-разметка совпала с предыдущим
аудитом по флагу события на всех **12 087** проверенных объект-днях; среди
**33 025** кандидатов текущей экспериментальной сборки совпали `y` и
известность исхода. Добавлены регрессионные тесты для изменения охраны
после тревоги, одновременного изменения, пропусков, продления дат и
формирования кандидатов только по сегодняшним данным.

Исходный артефакт головы `C` сервиса остаётся обученным на прежней метке.
Новая v2-разметка пока не подключена к автоматическому переобучению и
инференсу. Прибавка ML над простым правилом на полной очереди не даёт
достаточных оснований для такой замены.

## Решение и следующий критерий

Для MVP допустимо показать приоритизацию **проверок сигналов СМВУ** с
ограниченным дневным бюджетом, раскрывая свежесть охраны и неизвестные
исходы. Результат нельзя выдавать за прогноз реального проникновения.
Плановые Precision >0,7 и Recall >0,5 вместе не достигнуты.
Прогноз «завтра» относится к окну ближайших 24 часов; он не гарантирует
**24 часа запаса до события**. Ответы организаторов допускают обосновать
другой горизонт, но это необходимо явно объяснить.

Следующий значимый критерий для более сложной модели: обойти простое
правило на новых временных данных, отдельно в общей очереди и на первых
эпизодах, при одинаковом бюджете и учёте неизвестных исходов.
Для оценки настоящей безопасности нужны подтверждённые решения охраны
или журналы допусков, которых в выдаче нет.

Воспроизведение:

```powershell
python scripts/build_intrusion_eventtime_labels.py
python scripts/exp_intrusion_operational_queue.py
python scripts/exp_intrusion_operational_checks.py
python -m pytest tests/test_intrusion_target_v2.py tests/test_intrusion_operational_queue.py -q
```

Исходные цифры: [полная очередь](intrusion_operational_queue.json),
[проверка правил и интервалов](intrusion_operational_checks.json),
[сборка версии метки](intrusion_eventtime_v2_build.json).
