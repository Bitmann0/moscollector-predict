# Предиктивная аналитика инженерных коллекторов АО «Москоллектор»

Прогноз отказов и рисков по журналу событий системы мониторинга СМВУ.
Задача №8 ДЖКХ, условие — в [docs/ТЗ.md](docs/ТЗ.md).

Здесь расчётная часть: приём данных, фичестор, модели, контракт выдачи, REST
API и модуль формирования заявок. Веб-интерфейс диспетчера подключается к этому
API и живёт отдельно.

Что именно получит заказчик и какие границы у пилота — в
[описании поставки](docs/CUSTOMER_DELIVERABLE.md).

сценарии. Полнота выше 0,5 только у подтопления, при точности 21,9%.
Рабочую точку задаёт лимит рекомендаций, метки — прокси из
телеметрии СМВУ, январь–июнь 2026 просматривался многократно

Пожар и подтопление вошли в продукт 29.09.2026, хотя точность у них ниже 50%

[FIRE_FLOOD_PRODUCT.md](reports/FIRE_FLOOD_PRODUCT.md).

Расчёт одного дня по A_link, D, B и E (`POST /api/v1/score`) занимает 9,08 с
по медиане и не больше 10,63 с: замер 29.09 за 01–30.06 на машине

| направление ТЗ | сценарий в продукте | голова |
|---|---|---|
| Отказ датчика | Отказ датчика: риск потери связи | `A_link` |
| Износ инфраструктуры | Износ: плановая диагностика оборудования | `D`, правило `n_bad_w7` |
| Несанкционированный доступ | НСД: проверка объектов с хроническими охранными тревогами | `guard_weekly` |
| Пожарный риск | Пожар: риск пожарной или газовой тревоги на участке | `B` |
| Подтопление: в четыре направления карточки не входит, названо в задачах сервиса полного ТЗ (§4) | Подтопление: риск затопления насосной на объекте | `E` |

Остальные головы [configs/heads.yaml](configs/heads.yaml) — исследовательские
и в продукт не выдаются. Почему отклонены дневная охранная очередь `C`,
`A_strict`, температура и «Обнаружен газ» — в реестре, раздел
«Отклонённые постановки».

### Почему не достигнуты пороги

ТЗ называет источники, которых заказчик не предоставил и, по прямому ответу
экспертов, не предоставит: журналы ОДС, реестр оборудования, АРМ-Контроль,
координаты. Следствия конкретны:

- **Пожарный риск** по ТЗ строится на корреляции с графиками сварочных и
  горячих работ из АРМ-Контроля. Их нет: история тревог участка улучшила
  прокси-прогноз, но он не равен прогнозу подтверждённого пожара. В продукте
  это ручная очередь, в которой подтверждается 8,6% рекомендаций.
- **Износ** по ТЗ строится на датах ввода в эксплуатацию и истории ремонтов.
  Их нет, возраст подменён датой первого появления канала в журнале.
- **Несанкционированный доступ** по ТЗ строится на СКУД и журналах допусков.
  Их нет, но нашлась частичная замена в самом журнале СМВУ: события постановки
  и снятия с охраны, 47 объектов из 78.
- **Устойчивый отказ датчика** (голова `A`) при базе 0,2 % ранжируется
  прилично (ROC-AUC 0,920 в прежнем протоколе, `reports/final_metrics.csv`),
  но точности 0,7 не достигает ни при каком пороге. Это предел источника.

## Запуск

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[api,dev]"
.venv/Scripts/python -m pytest -q
```

Сборка с нуля — одна команда. Она сама решает, что устарело:

```bash
.venv/Scripts/python -m mkl.cli run
```

Что происходит и что уже свежее:

```bash
.venv/Scripts/python -m mkl.cli status
```

Стадии объявлены в [src/mkl/pipeline.py](src/mkl/pipeline.py): `ingest` →
`states`, `panel`, `weather` → `features` → `train`. Стадия считается
устаревшей, если хоть один её вход новее любого выхода; приём вдобавок зависит
от собственного кода, потому что правка дедупликации меняет данные.
После приёма и панели `python scripts/verify_ingest.py` сверяет события и
`daily_channel` с аудитом исходных CSV в `../analysis/` и пишет
`reports/ingest_reconciliation.json`.
Реестр фич `configs/features.yaml` создаётся локально вместе с фичестором:
он содержит путь и время сборки конкретной машины и поэтому не хранится в Git.

Полная сборка занимает около полутора часов: приём 6 минут, панель 31 минуту,
фичестор 22 минуты, переобучение остальное.

Новые журналы кладутся в `data/raw/ext-journal-YYYY.csv` (текущий год можно
заменять обновлённой выгрузкой). Команда `mkl run` сама находит годы, пересобирает
зависящие от них стадии, продлевает погоду до доступной даты и переобучает модели.
Для сервиса последние 30 наблюдаемых суток выбирают порог алерта, предыдущие
30 калибруют вероятности, а обучение заканчивается до них с embargo из
`configs/heads.yaml`. Каждая модель сохраняется атомарно; пока её запись не
завершена, сервис читает прежний артефакт. При отсутствии свежей архивной погоды
соответствующие признаки остаются пустыми, без подстановки будущих значений.

### Модели для исторических дней: окно демо

Пилотную модель сервис принимает для дня расчёта `asof`, только если окно
выбора порога кончилось за 1…`max_model_lag_days` суток до него
(`serve.validate_pilot_artifact`; у A_link, B и E 8 суток, у D 14). Модель по всем
данным с порогом по 29.06 проходит проверку только для 30.06. Остальным дням
июня нужны модели по данным, обрезанным раньше.

`--source-end C` показывает обучению данные такими, какими они были к концу
суток C: панель режется по суткам, эпизоды — по концу, групповые отказы и флаг
`is_group` пересобираются по оставшимся эпизодам (`db.attach_label_sources`).
Всё это до построения меток. Артефакт пишется в
`models/{голова}@{конец окна порога}.pkl`, `models/{голова}.pkl` не
меняется. Конец окна порога — C минус горизонт, у A_link C − 1.

Отсечки для окна 01.06–30.06 (границы меняют `--window-start`, `--window-end`):

```bash
MKL_ROOT=<корень> .venv/Scripts/python scripts/train_latest.py A_link --window-plan
```

| `--source-end` | конец окна порога | годится для asof |
|---|---|---|
| 2026-06-01 | 2026-05-31 | 01.06–08.06 |
| 2026-06-09 | 2026-06-08 | 09.06–16.06 |
| 2026-06-17 | 2026-06-16 | 17.06–24.06 |
| 2026-06-25 | 2026-06-24 | 25.06–02.07 |

Обучение, по прогону на отсечку:

```bash
MKL_ROOT=<корень> .venv/Scripts/python scripts/train_latest.py A_link --source-end 2026-06-01
MKL_ROOT=<корень> .venv/Scripts/python scripts/train_latest.py A_link --source-end 2026-06-09
MKL_ROOT=<корень> .venv/Scripts/python scripts/train_latest.py A_link --source-end 2026-06-17
MKL_ROOT=<корень> .venv/Scripts/python scripts/train_latest.py A_link --source-end 2026-06-25
```

или все четыре подряд: `train_latest.py A_link --train-window`. Модели B и E
окна демо — `train_latest.py B E --train-window`, основные `B.pkl` и `E.pkl` —
`train_latest.py B E` ([пересчёт](reports/FIRE_FLOOD_PRODUCT.md)). `--out КАТАЛОГ`
кладёт артефакты с теми же именами в другой каталог, `--out ФАЙЛ.pkl` — в один
файл. Отчёт прогона — `reports/model_refresh@{C}.json`;
`reports/latest_model_refresh.json` остаётся от последнего обычного
переобучения. Строка в stderr «окно порога кончается …, план ждал …» значит,
что покрытие дней надо пересчитать по фактическому концу окна.

D — правило `n_bad_w7`, модель не обучается: порог пересчитывается по
понедельникам, задержка 8–14 суток при лимите 14 (`rule_head.py`).

Выбор в сервисе: `serve.artifact_path(голова, asof)` берёт из
`models/{голова}@*.pkl` файл с самым поздним концом окна порога раньше asof,
если задержка не больше `max_model_lag_days`. Иначе берётся
`models/{голова}.pkl`; для неподходящего дня его отклоняет проверка задержки, и
голова отвечает `stale`. Тот же выбор делают `serve.score` и
`product_api._pilot_artifact`, так что `threshold_end`, `model_lag_days` и
`model_version` в `/score` описывают файл, по которому посчитан риск. Дата в
имени сверяется с метаданными артефакта. Кэш `api._cache_generation` учитывает
все `models/*.pkl` с временем изменения.

На стенде не запускать: каждый прогон — полное обучение на всей истории, DuckDB
берёт до 10 ГБ памяти (`db.connect`). На стенд кладутся готовые артефакты.

Историческое сравнение на фиксированном периоде 2026-01-01 … 2026-06-30
запускается отдельно: `.venv/Scripts/python scripts/final_eval.py`. Его нельзя
смешивать с регулярным переобучением, потому что этот период уже многократно
использовался при разработке и не является новым слепым тестом.

## Встраивание в веб-приложение

Между моделью и интерфейсом стоит слой, который переживает переобучение:
наружу смотрит схема из [src/mkl/contract.py](src/mkl/contract.py), внутрь
уходят подробности про бэкенды, фичестор и отсечку бюджета.

### Из Python

```python
from mkl import service, workorders

alerts = service.daily_alerts()          # список Alert
orders = workorders.build(alerts)        # заявки на объект
gaps   = service.coverage()              # по кому голова не отвечает и почему
```

### Через REST

Продуктовый сервис — `mkl.product_api` в образе ML, порт 8001 внутри сети
compose: `GET /health`, `GET /ready`, `GET /api/v1/directions`,
`POST /api/v1/score`, `GET /api/v1/guard-weekly-inspections`,
`POST /api/v1/outcomes`. Бэкенд продукта вызывает только их
(`backend/app/services/ml_client.py`). Таблица ниже — прежний
исследовательский REST `mkl.api` (`mkl.cli api`).

| метод | что отдаёт |
|---|---|
| `GET /health` | готовность и список обученных голов |
| `GET /api/v1/directions` | направления ТЗ и закрывающие их головы |
| `GET /api/v1/alerts` | суточная выдача; фильтры по направлению и голове |
| `GET /api/v1/alerts/{id}` | карточка: адрес, окно прогноза, причины |
| `GET /api/v1/coverage` | покрытие каждой головы |
| `GET /api/v1/guard-signal-priorities` | отдельная ручная очередь объектов по риску записанного охранного сигнала СМВУ завтра; балл не является вероятностью |
| `GET /api/v1/guard-weekly-inspections` | узкая плановая очередь повторяющихся охранных сигналов с паузой между рекомендациями одного объекта; может быть пустой |
| `GET /api/v1/work-orders` | заявки; фильтр по срочности |
| `GET /api/v1/work-orders/{id}` | карточка заявки |

### Что в алерте

Поля, на которые интерфейс может опираться:

- `alert_id` — детерминирован от головы, сущности и суток. Повторный расчёт
  тех же суток даёт тот же идентификатор, то есть запись обновляется, а не
  дублируется.
- `case_key` — то же без даты. Длинный отказ порождает алерт каждые сутки, и
  без общего ключа диспетчер увидит тридцать происшествий вместо одного.
- `address` — объект, комплекс, вид объекта, пикет, канал, тип датчика. У
  пожарного риска `B` канала нет, вместо него участок: `segment` и подпись
  `segment_label` — «ПК 10–20» или «каналы без пикета» (`mkl.address.segment_label`);
  у подтопления `E` — только объект. Географических координат в данных нет и не
  будет, поэтому **карта объектов возможна только как линейная схема по пикетам**.
- `risk`, `rank`, `in_budget`, `above_threshold` — риск, место в суточном
  списке, попадание в бюджет выездов и в рабочую точку.
- `valid_from`, `valid_to`, `horizon_hours` — окно, к которому относится
  прогноз. Не меньше 24 часов, у головы износа 168.
- `factors` — вклад признаков **в эту строку** по TreeSHAP, с человеческими
  названиями из `mkl.explain.FEATURE_LABELS`; признак без подписи, например
  температурные агрегаты участка у `B`, отдаётся кодом. Отбираются только толкающие риск вверх; у строки низкого риска
  список пуст, и это честнее выдуманной причины.
- `status` — различает «риска нет» и «данных нет». Голова доступа отвечает
  только там, где известно состояние охраны, и молчание по остальным объектам
  читалось бы как «всё спокойно».

`schema_version` версионируется отдельно от моделей: переобучение головы схему
не меняет.

### Заявки

Формируются на **объект**, а не на канал: бригада выезжает по адресу, и три
алерта по трём датчикам одного объекта — это один выезд. Разные направления
по одному объекту остаются разными заявками: это разные работы и разные
бригады.

Срок исполнения берётся из горизонта головы, а не из регламента — регламентных
сроков ТО в выгрузке нет, и придумывать их нельзя.

### Почему нет оркестратора

Airflow, Dagster и подобное решают задачу распределённого расписания, которой
здесь не стоит: один репозиторий, батчевый расчёт раз в сутки, одна машина. Их
цена — инфраструктура, которую принимающей команде придётся поднимать и
понимать. Объявленного графа с проверкой свежести достаточно.

## Чему нельзя верить

Сквозной аудит 20.09 нашёл 16 подтверждённых дефектов, четыре из которых
меняли выводы. Три из четырёх были не ошибками в формулах, а ошибками в том,
**что считалось событием**. Это стоит держать в голове при доработке.

**Нормированная PR-AUC не сравнивает головы между собой.** При фиксированной
ROC-AUC 0,85 она меняется от 0,0985 до 0,672 по диапазону наших базовых
ставок — разброс 6,8 раза при одинаковой модели. По ней головы переставлялись
местами. Для сравнения — `roc_auc` и lift на бюджете; `pr_auc_norm` годится
только внутри одной головы при неизменной метке.

**Критерий отбора обязан быть той же величиной, что заявляемый результат.**
CUSUM выигрывал ROC во всех трёх фолдах и ронял точность на бюджете с 0,866 до
0,851. Отбирали бы по ROC — приняли бы и ухудшили голову.

**Рабочая точка выбирается на валидации.** Подбор порога по ответам
отложенного периода даёт точность, прижатую к ограничению до четвёртого знака,
и в проде недостижим: сервис режет по бюджету и выдаёт другой список.

**Отложенный период просмотрен многократно.** Счётчик — в
[reports/holdout_uses.md](reports/holdout_uses.md), печатается при каждом
запуске финального замера. Приведённые числа следует считать валидационными:
они не подогнаны намеренно, но и не защищены от подгонки протоколом. Другого
запечатанного среза взять неоткуда — данные заканчиваются 30 июня 2026.

**Утечки нет** — это проверено: при разрушенной связи «сущность — метка» внутри
суток ROC внутри суток равен 0,50 на всех проверенных головах.

**Сигнал D у насосов и вентиляторов приходит пакетом.** Метка D
(`labels.build_wear`) — тревога или плохое состояние агрегата за сутки либо
эпизод от часа (`MIN_FAILURE_DURATION_S`). У насосов 41 851 из 41 952 секунд
с «Неисправен» (99,76%) несут в ту же секунду ещё одно значение, у
вентиляторов — 30 891 из 31 053 (99,48%). Из секунд с тревогой таких у насосов
49 186 из 63 998, у вентиляторов 30 513 из 30 901. Окно —
01.01.2024–30.06.2026, числа — `same_second_state_audit` в
[reports/sensor_semantics_audit.json](reports/sensor_semantics_audit.json),
пересчёт — `python scripts/audit_sensor_semantics.py`. Такой «Неисправен» —
часть пакета записей, а не отдельное начало отказа, и попадание D означает
повтор записанного сигнала, а не подтверждённый износ. Дневная модель насосов
из PR #3 показала то же: все 646 положительных дней её теста содержат секунду
с несколькими значениями, а 88 из 146 попаданий пришлись на точки после
разрыва наблюдений
([pump-error-analysis.json](../analysis/experiments/deep-data-audit/pump-error-analysis.json)).

**Порядок записей внутри одной секунды не определён, а код от него зависит.**
`mkl.states.build_episodes` (`states.py`, строки 18 и 23–24) и
`mkl.panel.build_daily_channel` (`panel.py`, строки 22–46) сортируют события
канала только по `ts`, а порядок строк с равным `ts` SQL не задаёт. От него
зависят границы эпизодов в `episodes`, а в панели — `n_transitions`,
`max_flat_run`, `time_in_alarm_s`, `time_in_bad_s`, `max_hold_alarm_s`,
`med_hold_alarm_s`, `n_standing_4h`, `n_stale_24h`, `chatter_psi_alarm` и
`armed_eod`. Не зависят `n_events`,
`n_alarms`, `n_bad`, `max_gap_s` и `med_gap_s`. Поэтому правило D (`n_bad_w7`)
и метка A_link (L9c строится по дням наличия данных) устойчивы, а метка D
через эпизоды от часа и признаки A_link из `ROLLING_COLS`
(`features/base.py`) — нет. Исправление меняет признаки и метки и требует
переобучить датированные модели ML1-05b, поэтому до сдачи ограничение только
записано здесь, исправление — задача после сдачи. Разбор — в
[ревью ветки feat/ml-pipeline](../analysis/experiments/deep-data-audit/REVIEW_ML_PIPELINE_BRANCH.md),
замечание P1.

Отчёты `reports/head_a.md` и `reports/heads_bcd.md` написаны до аудита и
помечены как устаревшие.

## Принципы, которые нельзя нарушать

**Признаки считаются только через `mkl.features.compute.build_all`.** Любой
другой путь создаёт расхождение между обучением и инференсом.

**Между обучением и тестом всегда остаётся embargo** — не меньше горизонта
плюс максимальное окно признаков: 31 сутки, для головы износа 37.

**Модель связана с фичестором отпечатком состава признаков.** При несовпадении
скоринг падает с внятным сообщением, а не подставляет другие числа в те же
слоты.

**Бюджет алертов соблюдается точно.** Ровно k алертов, ничьи разрываются
ключами сущности. Отсечка по порогу давала перерасход до 1,92 раза.

**Дисбаланс лечится весом класса и калибровкой, а не пересемплированием.**

**Метрика всегда сообщается вместе с базовой ставкой.** Требование «точность
выше 0,7» без доли позитивов бессмысленно: при базовой ставке 0,6 такую
точность даёт случайное ранжирование.
