# Что известно о проверке и среде запуска

Источники: исходный файл `8. ДЖКХ.pdf` (разделы 9, 11, 17–19), условие
трека [`ТЗ.md`](ТЗ.md), опубликованные ответы экспертов
[`qa_experts.csv`](../reports/qa_experts.csv), сообщения чата задачи №8
от 15–24.09.2026. Это ограничения для реализации и отчёта, а не результаты
нашей модели.

## Среда

- В исходном PDF указаны Linux для серверной части, PostgreSQL 12+, поддержка
  не менее 20 одновременных пользователей, прогноз одного объекта не дольше
  300 секунд и обработка потоковых данных с задержкой не более 300 секунд.
- Конкретные CPU, RAM, VRAM, GPU и объём диска для проверки не названы. В
  ответах экспертов прямо сказано, что ресурсы для обучения и тестовый стенд
  командам не предоставляются; пакет с инструкцией организаторы запускают на
  собственных мощностях.
- Сообщения №160 и №368 предлагают командам гранты Yandex Cloud (номинал
  промокода 5 000 ₽, ограничения для GPU-VM). Это помощь разработке, а не
  спецификация оценочного стенда. Поэтому обязательный путь инференса и
  переобучения должен работать на CPU без CUDA.

## Эталон и качество

- В ответах экспертов: общего закрытого тестового периода и лидерборда нет,
  оценка проводится экспертами на их стендах. Фиксированной эталонной модели
  не объявлено.
- В исходном PDF целевые Precision и Recall предлагается определить по
  качеству данных при проектировании. В кратком условии трека приведены
  Precision > 0,7 и Recall > 0,5; ответ экспертов уточняет, что это плановые,
  а не жёсткие значения, и допускает обоснованное снижение для MVP.
- Нет достоверной разметки подтверждённых аварий, ложных тревог и ремонтов.
  Наши метки из телеметрии являются прокси. В отчёте нужно показывать их
  определение, долю событий и границы применимости.
- Период 2026-01-01 … 2026-06-30 уже многократно просматривался командой и
  не является слепым тестом. Для выбора признаков используем walk-forward
  до 2026 года; затем фиксируем выбранный вариант и отдельно показываем
  2026 как дополнительную, уже просмотренную проверку.

## Что это означает для сдаваемого сервиса

Пакет должен содержать инструкцию развёртывания и воспроизводимый расчёт
метрик на временных срезах. Для алертов считаем качество при лимите **в каждые
сутки**, а также на уровне эпизодов, чтобы длинная тревога не выглядела серией
независимых успехов. Отдельно замеряем время CPU-инференса и объём памяти.

Текущий полный пересчёт суточной панели занял 4 949 секунд на машине
разработки; он не удовлетворяет требованию задержки потока ≤300 секунд.
Существующий контур пригоден для пакетного обновления истории и моделей, но
для почти рабочего сервиса нужен отдельный инкрементальный расчёт признаков
нового дня и точный входной контракт для событий СМВУ. Отсутствие настоящего
потокового API заказчика означает, что на хакатоне его можно только
эмулировать; ответ экспертов разрешает шаблоны и эмуляцию внешних интеграций.
