# Быстрый пересчёт кандидатов для будущих данных

25.09.2026. Полный фичестор проекта исторически пересчитывается долго. Для
рабочей недельной охранной очереди сначала проверили минимальный инкремент:
состояние объекта «на охране» и давность последней смены режима можно получить
из журнала событий на новый `asof`, не пересобирая весь объектный фичестор.

Проверка сравнивает SQL-запрос по событиям с уже построенной таблицей
`object.parquet` на трёх датах. В обоих случаях кандидат — `obj_armed = 1` и
`days_since_arm_event <= 7`.

| Дата | Время запроса по событиям | Строк | Расхождение состояния | Расхождение возраста | Расхождение кандидатов |
|---|---:|---:|---:|---:|---:|
| 2024-06-17 | 5,7 с | 55 | 0 | 0 | 0 |
| 2025-06-16 | 8,3 с | 52 | 0 | 0 | 0 |
| 2026-06-29 | 10,3 с | 53 | 0 | 0 | 0 |

Это значит, что после приёма новой пачки можно быстро проверить свежесть
охранного состояния и понять, есть ли кандидаты. Время относится только к
этому шагу; он **не** пересчитывает все погодные, канальные и объектные
признаки и не является полной гарантией цикла менее 300 секунд.

## Что можно подключать в сервис

1. Принимать новую пачку и строить `asof` из событий с проверкой схемы,
   дубликатов и границы времени.
2. Запускать быстрый guard-state refresh; сохранять число строк, время,
   последнюю дату и расхождение с предыдущим снимком.
3. Если полный фичестор и событийный v2-кэш готовы, строить очереди и
   сохранять прогноз. Если нет — отдавать `stale`/`no_data`, а не старый
   список.
4. После полного инкрементального обновления признаков сверять быстрый снимок
   с фичестором на одном дне; расхождение блокирует выдачу.

Скрипт проверки: `python scripts/exp_guard_fast_candidates.py`.
Это инфраструктурный прототип. Он не меняет границу качества моделей и не
добавляет новые автоматические заявки.
