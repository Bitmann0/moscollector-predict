# МосКоллектор — предиктивное обслуживание

Веб-сервис для раннего выявления деградации датчиков СМВУ. Первый MVP анализирует
частоту событий, тревожность, короткие повторные срабатывания («дребезг») и стабильность
значений, ранжирует каналы для проверки и позволяет создать черновик заявки.
Прогноз отказа на 24 часа пока не реализован; индекс 0–100 не является вероятностью.

> Текущий алгоритм — объяснимый baseline без учителя. Он нужен для проверки полного
> продуктового контура на предоставленном примере. Для подтверждения целевых метрик
> Precision > 0,7 и Recall > 0,5 необходимы размеченные журналы неисправностей и ремонтов.

## Быстрый запуск

Требования: Python 3.11+.

```bash
make install
make test
make dev
```

Откройте <http://localhost:8000>. Документация REST API доступна на
<http://localhost:8000/docs>.

CSV-файлы из `dataset.zip` уже могут находиться в `data/raw/`. Если репозиторий клонирован
заново, распакуйте туда:

- `журнал_событий_пример.csv`;
- `справочник_каналов_датчиков.csv`;
- `справочник_объектов_диспетчер.csv`.

Исходные выгрузки, архивы, PDF ТЗ и локальная SQLite-база исключены из Git. Это защищает
репозиторий от тяжёлых файлов и случайной публикации рабочих данных.

Альтернативный запуск через Docker:

```bash
docker compose up --build
```

Каталог `data/raw` подключается к контейнеру только для чтения, а база заявок хранится в
отдельном Docker volume.

## Что уже работает

- загрузка и валидация CSV СМВУ;
- построение признаков по каждому каналу;
- объяснимый эвристический индекс проверки за последнее окно данных;
- дашборд, условная схема каналов, фильтрация и текущие оценки;
- создание черновиков заявок вручную и автоматически для высоких рисков;
- REST API и Swagger/OpenAPI;
- SQLite-журнал заявок;
- модульные и API-тесты.
- GitHub Actions для линтинга, тестов и проверки сборки контейнера.

## API

- `GET /api/v1/health` — живость процесса (200), состояние и свежесть данных;
- `GET /api/v1/ready` — готовность анализа: 200 или 503;
- `GET /api/v1/summary` — показатели дашборда;
- `GET /api/v1/forecasts` — прогнозы с фильтрами;
- `GET /api/v1/forecasts/{channel_id}` — карточка риска;
- `GET /api/v1/maintenance-requests` — журнал заявок;
- `POST /api/v1/maintenance-requests` — черновик по прогнозу;
- `POST /api/v1/maintenance-requests/auto` — черновики для high/critical.

Подробности архитектуры и дорожная карта находятся в [docs/architecture.md](docs/architecture.md).
Правила командной разработки находятся в [CONTRIBUTING.md](CONTRIBUTING.md).

## Режимы версии 0.2

По умолчанию `MOSCOLLECTOR_MODE=historical`: старые данные разрешены, черновики
учебные. В режиме `live` отсутствие, устаревание или будущая дата данных дают
`/ready=503` и блокируют создание черновиков с HTTP 409. Свежесть проверяется при
каждом запросе; для загрузки новой выгрузки нужен перезапуск.

- `MOSCOLLECTOR_TIME_ZONE=Europe/Moscow` — допущение для времени CSV; API отдаёт UTC.
- `MOSCOLLECTOR_ANALYSIS_WINDOW_HOURS=24` — окно признаков до последнего события.
- `MOSCOLLECTOR_MAX_DATA_AGE_HOURS=6` — демонстрационный предел свежести, не норматив ТЗ.
- `MOSCOLLECTOR_FORECAST_HOURS=24` — цель будущей модели; не влияет на индекс.

Поля оценок `predicted_at`, `valid_until`, `horizon_hours` равны `null`.
Используйте `assessed_at`, `data_as_of`, `last_observed_at`, `score_kind`.
Путь `/forecasts` сохранён для совместимости. История оценок не сохраняется.
Сервис читает только пример событий и справочник каналов; годовые архивы и справочник
объектов пока не подключены. Весь архив нельзя просто загрузить в Pandas этого MVP.

[Критическое ревью](analysis/REVIEW_OTHER_IMPLEMENTATION.md) и
[исправления и следующая очередь работ](docs/review-resolution.md).

Карточка канала сохраняет решения диспетчера через GET/POST /api/v1/forecasts/{channel_id}/feedback. Снимок содержит режим и дату источника; автор указан вручную и не подтверждён аутентификацией. Решения пока нельзя считать проверенной разметкой.
