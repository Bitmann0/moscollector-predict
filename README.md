# Предиктивная аналитика инженерных коллекторов АО «Москоллектор»

ML-пайплайн прогнозирования отказов и рисков по журналу событий системы
мониторинга СМВУ. Часть проекта, отвечающая за модели и фичестор; веб-интерфейс
диспетчера, карта объектов и модуль заявок подключаются к описанному ниже API.

## Что внутри

| Слой | Модуль | Назначение |
|---|---|---|
| Приём | `mkl.ingest` | CSV → Parquet, дедупликация, справочники, разбор пикетов |
| Состояния | `mkl.states` | эпизоды неисправности, выделение групповых отказов |
| Панель | `mkl.panel` | суточная панель канал × сутки |
| Признаки | `mkl.features.compute` | единая точка расчёта для обучения и инференса |
| Фичестор | `mkl.store` | партиционированный Parquet, реестр, срезы |
| Разметка | `mkl.labels` | построители меток по семи головам |
| Валидация | `mkl.cv`, `mkl.metrics` | walk-forward с embargo, метрики под бюджет алертов |
| Обучение | `mkl.train`, `mkl.calibrate` | LightGBM, изотоническая калибровка |
| Скоринг | `mkl.serve` | прогноз и отсечка по бюджету алертов |
| Журнал | `mkl.experiments` | машиночитаемая история экспериментов |

## Головы моделей

Состав и параметры — в `configs/heads.yaml`. Каждая голова описывается
сущностью, набором признаков, меткой, горизонтом, величиной embargo и бюджетом
алертов на сутки.

| Голова | Сущность | Что прогнозирует |
|---|---|---|
| `A` | канал × сутки | канал перестанет быть доступен: отказ или уход в молчание |
| `A_strict` | канал × сутки | аномальное поведение конкретного датчика |
| `A_deg` | канал × сутки | деградация: переход в состояние неисправности |
| `A_prime` | объект × сутки | массовый отказ каналов объекта |
| `B` | объект × участок × сутки | пожарный риск участка: дым, газ, перегрев |
| `C` | объект × сутки | несанкционированный доступ |
| `D` | агрегат × сутки | износ насосов, вентиляторов, ИБП, люков |

## Результат на отложенном периоде

Период 2026-01-01 … 2026-06-30 не использовался ни в одном эксперименте до
финального замера.

| Голова | Базовая ставка | PR-AUC | Precision 0.7 при Recall | Precision при Recall 0.5 | lift | Цель ТЗ |
|---|---|---|---|---|---|---|
| `A` отказ датчика | 0.263 | 0.711 | **0.586** | 0.730 | 3.5 | да |
| `A_prime` массовый отказ объекта | 0.212 | 0.746 | **0.714** | 0.826 | 4.2 | да |
| `C` несанкционированный доступ | 0.147 | 0.661 | 0.446 | 0.667 | 5.0 | нет |
| `D` износ агрегатов | 0.432 | 0.676 | 0.423 | 0.673 | 2.2 | нет |
| `A_strict` аномалия датчика | 0.010 | 0.200 | — | 0.189 | 27.5 | нет |
| `A_deg` деградация датчика | 0.012 | 0.157 | — | 0.133 | 15.2 | нет |
| `B` пожарный риск участка | 0.012 | 0.048 | — | 0.036 | 7.5 | нет |

Требование ТЗ «Precision > 0.7 и Recall > 0.5» выполняют головы `A` и
`A_prime`. Разбор причин по остальным — в `reports/final.md`; коротко: пожарному
риску не хватает данных АРМ-Контроля по сварочным работам, износу — дат ввода
оборудования, редким головам — самой частоты события.

Время формирования прогноза по всем семи головам — **1,4 с** при нормативе
ТЗ 5 минут.

Метрики по каждой голове — в `reports/final.md`, история выбора конфигураций —
в `reports/head_a.md` и `reports/heads_bcd.md`, отчёт качества данных —
в `reports/data_quality.md`.

## Запуск с нуля

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -e . pytest pyyaml tabulate
.venv/Scripts/python -m pytest tests -q
```

Далее по порядку (каждый шаг сохраняет результат на диск и может выполняться
независимо):

```bash
.venv/Scripts/python -m mkl.ingest            # CSV -> Parquet, отчёт качества
.venv/Scripts/python scripts/build_states.py  # эпизоды и групповые отказы
.venv/Scripts/python scripts/build_panel.py   # суточная панель
.venv/Scripts/python scripts/fetch_weather.py # погода Москвы (необязательно)
.venv/Scripts/python scripts/build_features.py # фичестор
.venv/Scripts/python scripts/exp_a_failure.py  # выбор конфигурации головы A
.venv/Scripts/python scripts/exp_other_heads.py # остальные головы
.venv/Scripts/python scripts/final_eval.py     # отложенный период, сохранение моделей
.venv/Scripts/python scripts/make_reports.py   # отчёты
```

## Интеграция с интерфейсом

Прогноз по одной голове:

```python
from mkl import serve

df = serve.score("A")            # последний доступный срез фичестора
df = serve.score("A", asof=date(2026, 6, 30))   # конкретные сутки
```

Возвращается таблица с ключами сущности, колонкой `risk` (откалиброванная
вероятность) и булевым `alert`, выставленным по бюджету алертов из
`configs/heads.yaml`. Сортировка — по убыванию риска.

Прогноз по всем обученным головам сразу:

```python
scored = serve.score_all()       # {имя головы: таблица}
```

Состав фичестора и типы колонок описаны в `configs/features.yaml`; он
перезаписывается при каждой сборке признаков и служит контрактом между
пайплайном и потребителями.

## Принципы, которые нельзя нарушать при доработке

**Признаки считаются только через `mkl.features.compute.build_all`.** Любой
другой путь расчёта создаёт расхождение между обучением и инференсом. Тесты
`tests/test_store.py` проверяют, что добавление будущих суток не меняет
признаки прошлых.

**Между обучением и тестом всегда остаётся embargo** — не меньше горизонта
прогноза плюс максимальное окно признаков (31 сутки, для головы износа 37).
Величина задана в `configs/heads.yaml` и проверяется в `tests/test_cv.py`.

**Отложенный период 2026-01-01 … 2026-06-30 используется только в
`final_eval.py`.** Ни один эксперимент по выбору конфигурации его не касается.

**Дисбаланс лечится весом класса и калибровкой, а не пересемплированием.**
Oversampling портит калибровку вероятностей, не улучшая ранжирование.

**Метрика всегда сообщается вместе с базовой ставкой.** Требование
«Precision > 0.7» без указания доли позитивов бессмысленно: при базовой ставке
60% такую точность даёт случайное ранжирование. Для сравнения постановок разной
редкости используется нормированный PR-AUC, для операционной оценки —
точность в точке Recall 0.5 и lift.
